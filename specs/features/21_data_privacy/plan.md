## Approach

- Data, WebSocket, UI: no change. What each area answers for another user's record, the sign-in check of the connection, the batches, and the acks are built by features 06 to 23, and the sample data by feature 26 (spec, "Not part of this feature"). This feature checks across the whole app that none of them crosses accounts, and adds one behavior: no answer of the API is kept by the browser.
- API (JSON under `/api`, as in [docs/api_contract.md](../../docs/api_contract.md)):
  - Every answer of an endpoint under `/api` carries `Cache-Control: no-store`: 200, 201, and 204, and the errors 400, 401, 403, 404, 409, and 422, `GET /api/csrf`, `GET /api/session`, and `DELETE /api/session` included (spec question 3). Today none does: the probe of 2026-11-09 (lane p24) saw `no-cache` on the errors and the 204s, and `max-age=0, private, must-revalidate` on the 200s and 201s.
  - Nothing else changes. Another user's record gets the answer of a missing one in each area's own format (spec question 1): 404 `{ "error": "not_found" }` for an id in the address (features 06, 08, 09, 13); 422 `validation_failed` with `collection_id` or `tag_ids` `not_found` for an id in a body (features 09 to 11); 200 `{ "notes": [] }` for a `collection_id` or `tag_id` filter (feature 17); `{ "type": "error", "error": "not_found" }` for an ack (feature 23); and a subscription parameter is ignored (feature 22).
  - No answer carries `Access-Control-Allow-Origin` (spec question 5): CORS stays off. The Gemfile has no `rack-cors`, and `config/initializers/cors.rb` holds only comments. A preflight `OPTIONS` from another origin finds no route and answers 404 with no permission header (probed on 2026-11-09).
- The browser (spec question 6): no change. No source file writes local storage, session storage, IndexedDB, or `document.cookie`. The only cookie is the session cookie, which the server sets (`httponly`).
- Decisions:
  - **`no_store` before every callback.** `ApplicationController` overrides Rails' private `process_action`: for a controller of the `Api` namespace (`self.class.module_parent == Api`) it calls `no_store` (Rails' `ActionController::ConditionalGet`, which writes `Cache-Control: no-store`), then `super`. So the header is set before the callbacks and the rescues run, and the 401 of `require_signed_in_user` (each controller's `prepend_before_action`), the 204 of a logout with no sign-in, and the `rescue_from` answers (400, 403, 404) carry it too. A `before_action` in `ApplicationController` would run after the subclasses' prepended checks, and an `after_action` is skipped when a callback halts or an action raises. Probed on 2026-11-09 (lane p24, a throwaway spec outside the repo): with the override, the 13 answers of item 2's list each carried exactly `no-store`, and `/up` kept Rails' default. The sign-in callbacks (`Auth::SessionsController`, which also inherits `ApplicationController`) are not under `/api`, so the namespace check leaves them as they are: spec question 3 names only `/api`.
  - **CORS and browser storage stay as they are.** Spec questions 5 and 6 need no code while no plan adds CORS or browser storage (planner notes). The plans of features 20, 22, and 23 add neither: feature 20's says "Nothing is kept in the browser's storage, and no request goes to another origin". Items 13, 21, and 22 fail if a later change adds either.
  - **One systematic request spec.** `backend/spec/requests/data_privacy_spec.rb` checks the HTTP API across accounts in one place. Two users sign in through the real callbacks, each in a browser of its own (`open_session`): me ("Ada Lovelace", Google) and the other user ("Grace Hopper", GitHub). The other user has the collection "Secret", the tag "private", and the active weekly note "Secret plan" in "Secret", with "private", due today, and one note in each other review state. I have "Work", "ruby", "Plan B", and my own notes in each state. A constant at the top of the file, `API_ROUTES`, lists every route under `/api` as method and path (`PATCH` and `PUT` both). The tables of the tests are built from it: the 401 table walks every route, and the address table every route with `:id`. The route guard (item 3) compares `API_ROUTES` with the app's route table, so a route that a later feature adds fails the guard until it is in `API_ROUTES`, and so in the 401 and address tables.
  - **Tables inside one test, not loops of tests.** Each test walks its table, collects every request whose answer differs from the expected one, and expects that list to be empty, so the failure message names each request, as feature 24's sweeps do. Test names stay plain string literals (brief, "Test names").
  - **Snapshots.** `workspace_of(user)` (new, `backend/spec/support/privacy_helpers.rb`) reads the user's row (the saved time zone and the profile), the user's sign-ins, and every column of the user's collections, tags, notes (the review fields and feature 17's search copies included), note tags, and review dismissals (feature 23), each ordered by id. A refused request leaves both users' snapshots equal (`eq`), `updated_at` included.
  - **The same answer as a missing record.** Each table sends the other user's id, a missing id (the largest id of the table plus 1,000), and `abc`, and expects one status and one body for the three, so an answer never tells whether the other user's record exists (spec edge case).
  - **The WebSocket.** `backend/spec/channels/data_privacy_channel_spec.rb` (`type: :channel`) checks the connection, the subscription, the first batch, the 60-second check, and the ack, with feature 22's helpers (`send_session_cookie`, `stub_signed_in_connection`) and feature 20's way of running the periodic timer (`ReviewRemindersChannel.periodic_timers`, then `subscription.instance_exec(&callback)`). The batches after a change are broadcasts on the user's stream, so the request spec checks them with `have_broadcasted_to(user).from_channel(ReviewRemindersChannel)`, as feature 20's request spec does, for the user who made the change and not for the other.
  - **The frontend.** `frontend/src/DataPrivacy.test.tsx` renders `<App />` with the fetch stub of feature 17's `src/NoteFilters.test.tsx`, which answers by method and full URL, and drives the fake WebSocket (`src/test/fakeWebSocket.ts`) as feature 20's tests do. jsdom has local storage and session storage but no IndexedDB, so a source scan covers the rest: `import.meta.glob('./**/*.{ts,tsx}', { query: '?raw', import: 'default', eager: true })`, test files and `src/test/` left out, as feature 24's light-theme check reads the sources. The Verify walkthrough reads the real browser's storage.
  - **Guards.** Apart from item 2, every behavior of this spec exists when this feature is built, under the AC IDs of features 05 to 26. The AC-21 tests check it across the app, so that `grep -r "AC-21"` finds each scenario and requirements.md 7's "A user cannot access another user's collections, tags, notes, or reminders". Items 3 to 25 are expected to pass at once. Each is kept as the guard of its scenarios and recorded under Deviations, with the temporary mutation its item names, which makes it fail.
  - **Time in tests.** Backend: `travel_to Time.utc(2026, 11, 9, 20, 0)` (`ActiveSupport::Testing::TimeHelpers`), as features 12 to 23 do: 2026-11-10 in Asia/Tokyo, 2026-11-09 in America/New_York and in UTC. Frontend: the reconnect test fakes only `setTimeout` and `clearTimeout`, as feature 20's tests do.
  - **Pipelined run.** Every feature in `Depends on` is built before this one (build order of 2026-11-09; feature 26 is built by another lane). If one is not Done when this Build starts, Build records that under Deviations (owner's standing instruction).
