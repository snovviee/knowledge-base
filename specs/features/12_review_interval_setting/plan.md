## Approach

- Data:
  - `users.time_zone` (string, null): the IANA name of the zone the app last reported in a session check, when the server knows it. Null until then, and after a session check that names a zone the server does not know (spec questions 1, 19).
  - `notes.review_interval` (string, not null, default `"none"`): `none`, `daily`, `weekly`, `monthly`, or `custom` (spec questions 4, 15). Existing notes get `none`.
  - `notes.review_interval_days` (integer, null): 1 to 365 while the interval is `custom`, else null (spec questions 5, 12, 15).
  - `notes.next_review_date` (date, null): set exactly when the interval is not `none` (spec edge case).
  - `notes.last_reviewed_date` (date, null): no request of this feature sets it; feature 13 does. Every change here keeps it (spec questions 11, 15).
  - Two migrations, one per table. No index: nothing here looks notes up by these columns. Features 15 to 17 add what they need.
- "Today": `User#today` is the current date in the user's saved zone, or in UTC when there is none (spec question 1). It is computed from `Time.current`, never from `Date.today`, which reads the server machine's zone. The periodic checks of AC-20 will use the same method (spec edge case).
- API (JSON under `/api`, as in [docs/api_contract.md](../../docs/api_contract.md)):
  - `GET /api/session`: the request may carry the header `X-Time-Zone: <IANA name>`. With someone signed in, a name the server's tz database knows is saved on the user; any other non-empty value saves none, so "today" is UTC; no header, or an empty one, leaves the saved zone (spec questions 1, 19). The zone is written only when it differs from the saved one. The answer is unchanged: 200 `{ "user": { "id", "display_name" } }`, or 401 `{ "error": "unauthenticated" }`, which saves nothing.
  - Every note in an answer (`GET /api/notes`, `GET /api/notes/:id`, the 201 of `POST`, the 200 of `PATCH`) gains `"review_interval"`, `"review_interval_days"` (a whole number or null), and `"next_review_date"` and `"last_reviewed_date"` (`"YYYY-MM-DD"` or null) (spec question 15).
  - `POST /api/notes`: the body may hold `review_interval`, `review_interval_days`, and `next_review_date`. Without `review_interval`, the interval is `none` (spec question 4). A schedule with no date (missing or null) gets the user's today plus the interval: daily +1 day, weekly +7 days, monthly +1 calendar month (the same day number, or that month's last day), custom + the days (spec questions 6, 8). A given date is kept, a past one included (spec questions 7, 10).
  - `PATCH /api/notes/:id`: the same three fields, each only when the body has it (feature 09 question 9). The interval after the edit decides: days count only for `custom`, and a date only for a schedule (spec edge case). An edit that sends only the interval keeps the date, and a `next_review_date` of null restarts the schedule from today (spec question 9). `none` removes the next review date and the days; leaving `custom` removes the days; the last reviewed date stays (spec questions 11, 15).
  - 422 `{ "error": "validation_failed", "fields": { ... } }`, one code per field, in the same answer as the other note fields' codes, with nothing created or changed (spec question 12; feature 09 question 8):
    - `review_interval`: `invalid` for any value but the five, null and values that are not text included.
    - `review_interval_days`: with `custom`, `blank` when missing or null, and `invalid` for anything but a JSON integer from 1 to 365 (`0`, `366`, `1.5`, `7.0`, `"7"`, `true`).
    - `next_review_date`: with a schedule, `invalid` for a value that is not text written `YYYY-MM-DD` naming a real date (`"20261109"`, `"2026-02-30"`, `"tomorrow"`, `""`, `20261109`).
  - Ignored, with no code: days with an interval other than `custom`, a date with `none` (even one that is not a date), and `last_reviewed_date` in any body (spec questions 12, 15).
  - Errors and their order: 401, 400, 403, then 404, as in features/09_notes_crud.
- WebSocket: none.
- UI:
  - `frontend/src/App.tsx`: `fetchSession` sends `X-Time-Zone` with `Intl.DateTimeFormat().resolvedOptions().timeZone`, and leaves the header out when the browser reports no zone. The page load and "Try again" both go through it. No other request sends the header: logout's `DELETE /api/session` keeps its exact arguments.
  - `frontend/src/reviewSchedule.ts` (new): the interval choices with their form labels ("None", "Daily", "Weekly", "Monthly", "Every N days"); the detail's label of a note's interval ("Weekly", "Every 10 days", "Every 1 day"); and `formatReviewDate("2026-11-16")` → "Nov 16, 2026". The date is built from its own year, month, and day with `Date.UTC`, and written with `Intl.DateTimeFormat('en-US', { month: 'short', day: 'numeric', year: 'numeric', timeZone: 'UTC' })`, so no browser zone moves a calendar date.
  - `frontend/src/Notes.tsx`: `NoteSummary` gains the four fields. Each list entry shows an element with `data-testid="note-review"`: "Next review: Nov 16, 2026", or "No review scheduled" (spec question 14). It is not a list item, so the AC-09 `listitem` queries keep their meaning. A field missing from an answer (the older test fixtures have none) reads as no schedule.
  - `frontend/src/NoteDetail.tsx`: two rows after "Tags": "Review interval" with "None", "Daily", "Weekly", "Monthly", or "Every N days" with the number ("Every 1 day" for one), and "Next review" with the date or "Not set" (spec questions 14, 16, 18).
  - `frontend/src/NoteForm.tsx`, in the new-note and the edit form, after the Tags group:
    - "Review interval": a select with the five choices (values `none` to `custom`). None in a new note, the note's interval in the edit form (spec question 18).
    - "Number of days": a text field with `inputMode="numeric"`, shown only while "Every N days" is chosen. The note's days in the edit form.
    - "Next review date (optional)": a field of `type="date"`, shown only while the interval is not None (spec question 7). The note's date in the edit form.
    - A hidden field keeps its value, so choosing its interval again shows it again. A hidden field is neither checked nor sent.
    - Browser checks on "Create" and "Save" (`checkNote`), shown as feature 09 shows them: with "Every N days", days that are empty after trimming are `blank` ("Enter the number of days."), and anything but digits naming 1 to 365 is `invalid` ("Enter a whole number from 1 to 365."). With a schedule, a date field whose `validity.badInput` is true is `invalid` ("Enter a valid date."). Nothing is sent, and the first field with a message gets the focus. `FIELDS` gains `review_interval`, `review_interval_days`, and `next_review_date` after `collection_id`, the order in which the form shows them.
    - The server's 422 codes for these fields show under them the same way; `review_interval` `invalid` shows "Choose a review interval." (spec question 13).
    - What a save sends (spec question 17). The new-note form sends `review_interval` only when it is not `none`, `review_interval_days` (a number) only with `custom`, and `next_review_date` only when the field holds a date. The edit form sends `review_interval` when it differs from the note's; `review_interval_days` when `custom` is chosen and the note's interval was not `custom` or the number differs; and `next_review_date` when the interval chosen is not `none` and the field differs from the note's date, with null for an emptied field.
- Decisions:
  - The schedule rules live in `Note`, not in the controller. A `before_validation` callback drops the days unless the interval is `custom`, and drops the date when it is `none`. Validations check the values as sent. A `before_save` callback fills the missing date of a schedule with `user.today` plus the interval. So every path that saves a note keeps the rule "a next review date exactly when the interval is not none": the API, `bin/rails runner` in the walkthrough, and the recalculation of feature 14.
  - Raw values are checked before the cast. Active Record turns `"7"`, `7.0`, and `1.5` into whole numbers, and `"2026-02-30"` or `"tomorrow"` into nil without an error (spec, Notes for Plan). So the validations read `review_interval_days_before_type_cast`, which must be an `Integer` from 1 to 365, and `next_review_date_before_type_cast`, which must be a `Date`, or a `String` that matches `\A\d{4}-\d{2}-\d{2}\z` and that `Date.valid_date?` accepts. A value read back from the database passes both.
  - The date is filled in `before_save`, after the validations, so a date that failed its check is never replaced by a computed one.
  - The controller assigns the review fields only when the body has their keys, and passes the raw values to the model, as `edited_attributes` already does for the other fields (feature 09 question 9). `last_reviewed_date` is never read from a body.
  - Known zones: a name is known when `TZInfo::Timezone.get(name)` succeeds, and an unknown name raises `TZInfo::InvalidTimezoneIdentifier`. Only known names are saved, so `User#today` never meets an unknown one. TZInfo reads the zone data of the `tzinfo-data` gem, which `backend/Gemfile` installs on every platform (item 43). That data has the tz database's backward links, so the old alias names that Chromium reports for some zones, such as `Asia/Calcutta` and `Europe/Kiev`, are known and saved as sent (item 42). Until the revision of 2026-11-09, the gem was installed only for Windows and JRuby, and TZInfo read the backend image's `/usr/share/zoneinfo`, which has none of those names (Deviations).
  - The zone is set by a GET. Another site cannot set it: a cross-site page cannot add a custom header without a CORS preflight, and CORS is off (spec question 1).
  - Dates go out through `Date#as_json`, which writes `"2026-11-16"`. `created_at` and `updated_at` stay as they are (spec question 2).
  - Time in tests. Every backend test that depends on the date fixes the time with `travel_to` (`ActiveSupport::Testing::TimeHelpers`, included in each spec file, as `spec/requests/session_spec.rb` does), at 2026-11-09 20:00 UTC: an hour at which the zone changes the date (2026-11-10 in Asia/Tokyo). The frontend never computes "today", and its formatting is pinned to UTC, so its tests need no fake clock. Item 41 runs the AC-12 tests under `TZ=Pacific/Kiritimati` (UTC+14) and `TZ=Pacific/Pago_Pago` (UTC−11).
  - Earlier exact-shape assertions. Feature 09's `full_json` and the list's first entry in `spec/requests/notes_spec.rb` compare whole notes with `eq`, so they gain the four fields for a note with no schedule (`"review_interval" => "none"` and three nils), the way feature 10 item 19 added `tags`. No `expect` line changes. The same goes for any such helper in features 10 and 11's request specs.
  - Earlier frontend tests. Their fixtures carry no review fields, which read as no schedule, and the forms send no review field unless the schedule changed. So the AC-09 exact bodies stay as they are: the create `{ title, body, source_url, collection_id }` and the edit `{ title, body, source_url }`. The session stubs match the URL alone, or `GET /api/session` with the method defaulting to GET, so they still match a session check with a second argument. The one assertion with exact arguments on `/api/session` (`src/App.logout.test.tsx`, "AC-05 Log out sends the logout request with the CSRF token and shows the sign-in screen") checks the `DELETE`, which this feature leaves as it is.
  - The date field in tests (probe of 2026-11-09 in the frontend container): `user.type(field, '2026-11-20')` sets its value, and `user.clear(field)` empties it. jsdom never reports `badInput` (it turns an impossible date into `""`), so the bad-input test overrides the field's `validity` getter, for example with `vi.spyOn(field, 'validity', 'get')`.
  - The number of days is a text field with `inputMode="numeric"`, not `type="number"`, so the check sees what was typed ("1.5", "abc") and shows the spec's message for it, the same in every browser and in jsdom. The source URL field is built the same way (feature 09).
  - New test files, so the earlier ones keep their assertions: `spec/models/user_time_zone_spec.rb`, `spec/models/note_review_spec.rb`, `spec/requests/review_interval_spec.rb`, `spec/requests/time_zone_spec.rb`, `src/App.timeZone.test.tsx`, `src/reviewSchedule.test.ts`, and `src/ReviewInterval.test.tsx`. The frontend files use the fetch stub of `src/Notes.test.tsx`, which answers by method and path.

TZInfo uses the gem's data whenever the gem can be loaded, and the image's files only without it. Mapping the old names by hand in `known_time_zone` was not chosen either: it would be a list to keep in step with the tz database.
