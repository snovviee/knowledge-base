## Approach

- Data: no change. A reminder is computed from the notes of features 12 to 16 each time a batch is made, and nothing about a batch is stored. Feature 23 adds the dismissals.
- The batch (spec questions 1 to 3): `ReviewReminderBatch.for(user)` (new, `backend/app/models/review_reminder_batch.rb`, a plain class, as feature 15's `NoteListFilter` is) returns the message:
  - `{ "type": "review_reminders", "reminders": [ ... ] }`, built from `user.notes.due_today(today).or(user.notes.overdue(today))` (features 15 and 16; planner notes), with `today = user.today` read once (feature 12), ordered by `next_review_date`, then `created_at`, then `id`, with each note's collection loaded in the same query (`includes(:collection)`).
  - Each reminder: `type` `"review_due_today"` or `"review_overdue"` (`"review_"` and the note's state), `note_id`, `title`, `collection_name`, `next_review_date` as text `"YYYY-MM-DD"`, and `review_state` from `note.review_state(today)` (`"due_today"` or `"overdue"`). The values are ready for JSON (the date is text), so a channel test's `transmissions` and a broadcast read the same values.
  - No limit and no paging. With no reminder: `{ "type": "review_reminders", "reminders": [] }`.
- WebSocket: `ReviewRemindersChannel` (`backend/app/channels/review_reminders_channel.rb`, feature 22's channel, identifier `{"channel":"ReviewRemindersChannel"}`):
  - `subscribed` (private): `stream_for current_user`, then `send_batch`, which transmits the first batch at once (spec question 4). Action Cable confirms a subscription that streams only once its stream is set up, so the first batch usually arrives just before `confirm_subscription`. The client accepts a message of the subscription before or after the confirmation.
  - `periodically :send_batch, every: CHECK_INTERVAL` (`60.seconds`): while the subscription lives, it checks again every 60 seconds and transmits a batch each time, an unchanged one included (spec question 4). Each subscription has its own timer, which Action Cable stops when the subscription or the connection ends.
  - `send_batch` (private) makes the batch for the user read again from the database (`User.find(current_user.id)`), and transmits it. The connection's `current_user` is loaded once, when the connection opens, so a time zone saved later by another browser's session check would otherwise never apply (spec edge case "A zone saved by a load in another browser applies from the next batch").
  - `ReviewRemindersChannel.send_batch_to(user)` (a class method, so not an action): `broadcast_to(user, ReviewReminderBatch.for(user))`. Every subscription of that user, in every tab and browser, receives it through its stream. Action Cable's stream handler passes a streamed message to the channel's `transmit`, so feature 22's check of the sign-in applies to it too (spec question 5; feature 22 question 5).
  - Every message goes out through feature 22's private `transmit`, which sends nothing, and closes the connection with the refusal, once the connection's sign-in is gone.
  - On the wire (Action Cable's framing, which feature 22 documents): `{"identifier":"{\"channel\":\"ReviewRemindersChannel\"}","message":{"type":"review_reminders","reminders":[ ... ]}}`.
- Batches after a change (spec question 5): one broadcast call, `ReviewRemindersChannel.send_batch_to(current_user)`, made from one after-action, in a concern of this feature, that two controllers declare. It is the only place in the HTTP API that sends a batch, and it runs at most once per request:
  - `backend/app/controllers/concerns/sends_review_reminders.rb` (new): the private `send_review_reminders` calls `ReviewRemindersChannel.send_batch_to(current_user)` when the response is a success (2xx). A refused request (400, 403, 404, 409, 422) changed nothing and sends nothing. A 401 from `require_signed_in_user` halts the chain, and an exception that `ApplicationController` answers (403 `invalid_csrf_token`, 400 `bad_request`, 404 `not_found`) aborts it, so none of them reaches an after-action.
  - `Api::NotesController`: `include SendsReviewReminders` and `after_action :send_review_reminders, only: %i[create update destroy review]`. That covers a create, every edit (title, body, source URL, tags, schedule, a move with `collection_id`, an archive, a restore), a delete, and "Mark as reviewed" (feature 13). Two lines at the top of the class; no action changes.
  - `Api::CollectionsController`: the same two lines with `only: :update` (a rename). A collection create or delete changes no reminder: a new collection has no notes, and a collection with notes cannot be deleted (AC-07).
  - The after-action runs once the action has committed its change, so the batch holds it.
- UI:
  - `frontend/src/cable.ts` (feature 22) gains two handlers in `CableHandlers`, and its connection's life:
    - `onMessage(message)`: each message whose `identifier` is the reminders subscription's, before or after the confirmation. Pings, `welcome`, `confirm_subscription`, and other identifiers are not handed on.
    - `onLost()`: a close that no `disconnect` with `"reconnect": false` came before (a network failure, a server that stops, or a server restart's `"reconnect": true`), a connection that cannot be opened (an error, then a close), and a stale connection.
    - Retry: after a loss, the client opens a new connection on its own: 1 s after the loss, then each wait doubles, up to 30 s, and stays at 30 s. A `welcome` resets the wait to 1 s. So two attempts are never more than 30 s apart (spec question 8).
    - Stale: an open connection that receives no frame at all for 10 s (Action Cable sends a ping every 3 s) is closed by the client and counted as lost. The timer runs only while the socket is open.
    - A `disconnect` with `"reconnect": false` still calls `onSignedOut` and is never retried (feature 22 question 3). `close()` closes the current socket and cancels a pending retry and the stale timer.
    - Only the current socket counts. A real socket fires its `close` event some time after the client called `close()` on it. So once the client has closed a socket itself (`close()`, or the stale check) or replaced it, every later event of that socket is ignored: its late `close` calls no handler and starts no retry, after the sign-in screen has taken the panel's place included (feature 22 question 3; spec question 10).
  - `frontend/src/ReviewReminders.tsx` (feature 22) becomes the panel: `<section aria-labelledby>` (the region "Review reminders") with the heading `<h2>` "Review reminders", which has `tabIndex={-1}` so that feature 23 can move the focus to it. Props: `onSignedOut` (feature 22), `onOpen(noteId)`, and `openDisabled`.
    - States (spec questions 6, 8): no batch yet: "Loading…" with `role="status"`. A batch: its reminders, in its order, or "No review reminders". Lost: "Review reminders are offline. Reconnecting…" with `role="alert"`, above the last list (or alone, in place of "Loading…", when no batch has come yet). The next batch removes the alert and replaces the list. The panel reads only a message whose `type` is `review_reminders`; any other message of the subscription (feature 23's error answers) changes nothing.
    - A reminder is a list item: the title, the collection name, "Overdue" or "Due today" (with the look of the notes list's label of features 15 and 16), "Next review: Nov 2, 2026" (feature 12's `formatReviewDate`), and the buttons "Open" and "Dismiss". Its React key is `` `${note_id}:${type}:${next_review_date}` `` (spec question 7), so a repeated reminder keeps its element, and the focus, wherever the new batch puts it.
    - "Open" calls `onOpen(note_id)`, and is disabled while `openDisabled`. "Dismiss" shows, enabled while the panel is online and disabled while it is offline (spec question 8). What "Dismiss" does is feature 23's, so in this feature it has no action.
    - The list scrolls inside the panel (`max-h-48 overflow-y-auto`, 12 rem), so the heading "Notes" stays on the first screen, also at 320 × 568 px (feature 25 question 7).
    - Look (feature 24 questions 3 to 5): the heading like the other area headings (`font-semibold`); the inner side padding of the header and the notes area (`px-4`); its texts `text-sm`, with the gray of the empty and loading lines and the red of alerts; "Open" and "Dismiss" as small row actions, with the classes of "Rename" and "Delete" in the collections list (hover and focus included).
  - `frontend/src/App.tsx`: the main area becomes a column beside the left area (`<div className="flex min-w-0 flex-1 flex-col">`): the panel at the top, then the notes area (spec question 6). `App` keeps `noteFormOpen` (state) and `notesRef` (`useRef<NotesHandle>(null)`). It passes `onOpen={(id) => notesRef.current?.openNote(id)}` and `openDisabled={noteFormOpen}` to the panel, and `ref={notesRef}` and `onFormOpenChange={setNoteFormOpen}` to `Notes`. A batch changes only the panel's own state, so the notes area, and a form open in it, never render again because of it.
  - `frontend/src/Notes.tsx`: two additions, and no change to its views:
    - `export type NotesHandle = { openNote: (id: number) => void }`, exposed with `useImperativeHandle(ref, ...)` (React 19 passes `ref` as a prop). `openNote(id)` shows the note's detail in place of the list or a detail, as choosing its title in the list does (feature 09 question 1). The detail view carries a counter that is part of the detail's React key, so "Open" on the note whose detail already shows loads it again and puts the focus on its title.
    - `onFormOpenChange?: (open: boolean) => void`, called from an effect keyed on whether the new-note or the edit form shows (spec question 9).
  - Nothing is kept in the browser's storage, and no request goes to another origin (feature 21 questions 5 and 6).
- Decisions:
  - **One batch per user, broadcast on the user's stream**, rather than a signal that each subscription answers with its own query: the batch is the same for each connection of a user (one "today", one set of notes), so a change costs one query. A request spec asserts it with rspec-rails' `have_broadcasted_to(user).from_channel(ReviewRemindersChannel).with(...)`, through the test adapter of `config/cable.yml`. A stream callback would be lost in channel specs, because Action Cable's test stub only records the stream's name.
  - **The trigger is one after-action that the controllers declare.** It lives in this feature's concern; lane A's notes controller gets two declarative lines and no change inside its actions. `raise_on_missing_callback_actions` is on in test and development (`config/environments/`), so `only:` names only existing actions; `review` exists since feature 13.
  - **The periodic check is Action Cable's `periodically`.** Channel specs start no timers (`ChannelStub#start_periodic_timers` does nothing), so a test reads `ReviewRemindersChannel.periodic_timers` (one timer, `every: 60.seconds`) and runs its callback on the subscription with `subscription.instance_exec(&callback)`, moving the clock with `travel_to`. No test sleeps. Probed on 2026-11-09 (lane p20, a throwaway spec outside the repo): `stream_for` shows as `have_stream_for(user)`; a `transmit` in a private `subscribed` is recorded and the subscription is confirmed; the timer's callback runs under `instance_exec` after `travel_to`; `have_broadcasted_to(user).from_channel(...).with(...)` matches a hash with symbol keys against the decoded message, and `not_to have_broadcasted_to(other_user)` holds.
  - **Channel specs compare with string keys.** `ReviewReminderBatch.for` returns symbol keys. Action Cable's channel-test stub keeps each transmitted message with indifferent access, whose keys are strings, so `eq` against a hash with symbol keys fails even when the values agree. A channel spec compares `transmissions` with `eq([ batch.deep_stringify_keys ])` (or uses `match`). Probed again on 2026-11-09 (lane p20, resumed run): `eq` with symbol keys is false, with `deep_stringify_keys` true, and `match` and `have_broadcasted_to(...).with(...)` accept either.
  - **requirements.md 7** asks for the test "WebSocket notifications are sent for notes due today or overdue": item 6 (the first batch through the channel), with items 8 (the 60-second check) and 13 (a batch after a change).
  - **Channel callbacks and helpers stay private.** A public method of a channel is an action that a client can call (feature 22); `subscribed` and `send_batch` are private. Feature 23 adds the only actions: `ack`, and the `perform_action` that answers any other message.

- **Zone and dates.** Pages open with `timezoneId: 'UTC'` unless the item names another zone. T is A's today on the server, printed after A's first page load by `rails.sh <slot> 'puts User.find_by!(provider_user_id: "a-20").today'`; T+n and T−n are n days later or earlier. The UI writes a date like "Nov 9, 2026", the API like `"2026-11-09"`.
- **Data.** `rails.sh` with `u = User.find_by!(provider_user_id: "<uid>")`: collections with `u.collections.create!(name: "...")`, notes with `u.notes.create!(title: "...", body: "B", collection: <collection>, review_interval: "weekly", next_review_date: <date>)` (`status: "archived"` for an archived one; no `review_interval` for one with none). Data written by `rails.sh` sends no batch: the development server's Action Cable adapter is `async`, which works only inside the server process, so a runner cannot reach the open connections, even with `ReviewRemindersChannel.send_batch_to`. Such data is made before the page opens, or the page is reloaded after it, or the next check picks it up. Before item 1, A has the collections "Work", "Books", and "Misc", and the notes "Old idea" (Work, T−7), "Rails tips" (Books, T), and "Later" (Books, T+3), created in that order. To bring "Rails tips" back for a later item: `rails.sh` `u.notes.find_by!(title: "Rails tips").update!(next_review_date: <T>)`, then reload.
- **watch.** Before `page.goto('/')`: `page.on('websocket', ws => ...)` records each `framereceived` and `framesent` payload with its time, and the `close`. Pings (`{"type":"ping",…}`) are left out. A "batch" is a received frame whose `message.type` is `"review_reminders"`; its "reminders" are `message.reminders`.
- **The panel** is `page.getByRole('region', { name: 'Review reminders' })`. "The entry of X" is its list item that holds the title X.
- **Waiting for a check.** The 60-second check runs inside the server, one timer per subscription, and nothing outside the server can start it. Verify does not sleep a fixed time: it polls `watch`'s list until the next batch frame arrives, at most 65 s after the socket's previous batch, while nothing else changes, and fails the item if none comes. Only items 4, 5, and 17 wait for the check. Any other item that needs a batch at once makes a change through the app (a rename with `kb.api` or the UI), which sends one right away.
- **Midnight.** Two zones exactly 24 hours apart stand in for midnight: `Etc/GMT+12` (UTC−12) and `Etc/GMT-12` (UTC+12). A page opened with `timezoneId: 'Etc/GMT+12'` saves that zone; D is then the user's today (`rails.sh` `puts u.reload.today`). `rails.sh` `u.update_columns(time_zone: "Etc/GMT-12")` moves the user's today to D+1, as midnight does. The page is not reloaded after that, because a reload saves the browser's zone again.
- **Losing the connection.** Playwright's `page.routeWebSocket(/\/cable$/, handler)`, set before `page.goto('/')`. The handler connects each page socket to the server (`const server = ws.connectToServer()`), so the page's frames reach the server, and hands the server's frames to the page with `server.onMessage((m) => ...)` by a mode the script sets: "pass" (the default, `ws.send(m)`), "hold" (kept in a list, which "release" sends on in order), or "silent" (dropped: the page receives nothing and sees no close, as when the network fails). "Drop it" is `ws.close({ code: 1001 })` on the page's side. "Keep it offline" makes the handler close each new page socket at once, without connecting it. "Allow it again" sets "pass" and stops closing new sockets. Before the first item that uses a route, Verify checks that a routed socket is accepted: it receives its `welcome`, its confirmation, and a batch.
