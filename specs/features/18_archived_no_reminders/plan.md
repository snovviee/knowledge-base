## Approach

- Data, API, WebSocket, UI: no change expected. This feature adds tests and documents.
- Where the rule already lives (spec question 1). Features 15 and 16 define "due today" and "overdue" only for active notes, in one place in `Note` (planner notes): `Note#review_state(today)` gives nil for an archived note, and `Note.due_today(today)` and `Note.overdue(today)` both build on `Note.active`. Every kind of review reminder calls them:
  - the notes view: `review_state` in every note of the notes API, which the list's and the detail's "Due today" and "Overdue" labels show (features 15, 16), and the "Review" filter's `due_today` and `overdue` (`NoteListFilter`, features 15 to 17);
  - the WebSocket: feature 20's batch (`ReviewReminderBatch`, `user.notes.due_today(today).or(user.notes.overdue(today))`), and so the "Review reminders" panel; feature 23's ack, which accepts only a current reminder (`ReviewAck`).
- Restoring (spec question 2). An archive and a restore change only `status` (feature 09 question 9), so the interval and the dates stay, and a restored note is reminded when it is due, like any active note. Feature 20 sends a batch right after both, and feature 23's dismissal ends only when the next review date changes, so it stays through an archive and a restore.
- Decisions:
  - **Every item is a guard.** Each test is expected to pass when it is written, because features 15 to 17, 20, and 23 already hold the behavior. Build proves that each one can fail with the temporary mutation that its item names (applied to a copy, or reverted at once), and records each under Deviations (owner's standing instruction; brief, Build). A test that fails for the right reason shows a real gap: Build then writes the least code that makes it pass, in the file the gap belongs to, and records that under Deviations.
  - **Mutations target the shared rule, not a copy of it.** Most guards fail under the same mutation, `Note.active` dropped from `Note.due_today` and `Note.overdue` (or the status check dropped from `Note#review_state`). That is the point: one rule serves every kind of reminder, so one change to it breaks each kind, and each kind has its own test.
  - **requirements.md 7** asks for the test "Archived notes do not generate review reminders": item 2, by that name.
  - **"On its date" without waiting.** The batch a check sends is `ReviewReminderBatch.for(user)` at that moment (feature 20, items 8 and 9), so a request spec reads `ReviewReminderBatch.for(ada)` after `travel_to` the date instead of running the channel's timer.
  - Time in tests, as in features 15 to 20: `travel_to Time.utc(2026, 11, 9, 20, 0)` for a user with no saved zone, so today is 2026-11-09; midnight cases travel to 23:59:30 and then 00:00:30 UTC. A check's batch is made by running the channel's periodic timer callback on the subscription (`subscription.instance_exec(&callback)`, feature 20), never by sleeping. The frontend computes no date.
  - Channel specs, as in features 20 and 23: the connection is `stub_signed_in_connection` (feature 22's `spec/support/cable_helpers.rb`), `transmissions` are compared with string keys (`deep_stringify_keys`), and a broadcast with `have_broadcasted_to(user).from_channel(ReviewRemindersChannel)`.
  - **New test files**, and no change to any other file: `spec/models/archived_reminders_spec.rb`, `spec/requests/archived_reminders_spec.rb`, `spec/channels/archived_reminders_spec.rb`, and `src/ArchivedReminders.test.tsx` (the fetch stub of `src/ReviewDueToday.test.tsx`, feature 15). A test that fails for the right reason (a real gap, Decisions above) changes the one production file the gap belongs to, named under Deviations.
  - Pipelined run: this feature is built after features 17, 20, and 23, by whichever lane is free. If one of them is not Done when this Build starts, Build records that under Deviations (owner's standing instruction).
