  - The checks run one after another, each with `docker compose run --rm`, and each one's own output shows as it runs. A check passes when its command ends with status 0, so a check that cannot start (an image that fails to build, a container that cannot be created) fails (spec questions 2, 7):
    - plain `bin/test`: "RSpec" `docker compose run --rm -e TZ=UTC backend bundle exec rspec`; "Vitest" `docker compose run --rm -e TZ=UTC frontend npx vitest run`; "TypeScript" `docker compose run --rm frontend npx tsc -b`; "RuboCop" `docker compose run --rm backend bundle exec rubocop`; "ESLint" `docker compose run --rm frontend npx eslint .`;
    - `bin/test --time-zones`: for each zone, in the order UTC, Pacific/Kiritimati, Pacific/Pago_Pago, "RSpec (<zone>)" `docker compose run --rm -e TZ=<zone> backend bundle exec rspec`, then "Vitest (<zone>)" `docker compose run --rm -e TZ=<zone> frontend npx vitest run` (spec questions 8, 10).
  - After the last check: a blank line, one line per check in the order run, "<name>: passed" or "<name>: failed", then "All <N> checks passed." or "<n> of <N> checks failed.", where N is 5, or 6 with `--time-zones`. Status 0 when every check passed, 1 otherwise (spec questions 2, 7, 10).
  - It never runs Brakeman or bundler-audit (spec question 1), and never `docker compose up`, `exec`, `stop`, or `down`, so the app's own containers are left as they are, running or not (spec question 3).
- No network in the backend tests (spec question 4): the `webmock` gem in a `:test` group (`require: false`), and `backend/spec/support/webmock.rb` with `require "webmock/rspec"` and `WebMock.disable_net_connect!(allow_localhost: true)`. A request to another host raises `WebMock::NetConnectNotAllowedError` ("Real HTTP connections are disabled. Unregistered request: ...") before a connection is opened. This machine (`localhost`, `127.0.0.1`, `::1`) is let through.
- No network in the frontend tests (spec question 4): `frontend/src/test/networkGuard.ts` (new), installed by `frontend/src/test/setup.ts`, which runs before every test file:
  - `guardFetch(fetch)`, `guardXMLHttpRequest(XMLHttpRequest)`, and `guardWebSocket(WebSocket)` each refuse a URL whose host is not this machine, read against the page's address, so a relative URL is local. `fetch` rejects, `open` throws, and the constructor throws, each with "Blocked a request to another host in a test: <url>". The URL is recorded, and the real one is never called. A local URL goes to the real one with its arguments.
  - This machine: `localhost` and names that end in `.localhost`, `127.0.0.0/8`, and `[::1]`.
  - `installNetworkGuard({ target, afterEach })` puts the three guards on `target` by plain assignment, and registers an `afterEach` that throws "A test tried to reach another host: <urls>" when the test made a refused request, then clears the record. So the test fails even when the code under test caught the refusal: the app's code catches failed requests to show its messages.
  - `takeBlockedRequests()` returns the record and clears it. Only the guard's own tests use it, after the refusals they make on purpose.
  - Each test file keeps its own `vi.stubGlobal('fetch', ...)`, which sits on top of the guard, as now.
- Time in tests (spec question 5): no new code. The rule feature 12 started applies to every feature: a test whose result depends on the date fixes the time (`travel_to` in RSpec; `vi.useFakeTimers()` with `vi.setSystemTime(...)` in Vitest), and `bin/test --time-zones` proves it (item 14).
- Decisions:
  - **A POSIX `sh` script.** The host has no Ruby or Node (project.md), and the spec names macOS, Linux, and WSL 2 (feature 30 question 5). The script uses only POSIX shell and `docker`. Its tests run it in the backend container, where `/bin/sh` is `dash`, a strict POSIX shell; Verify runs it on macOS, where `/bin/sh` is bash in POSIX mode.
  - **`bin/test` is tested with a fake `docker`.** `backend/spec/scripts/bin_test_spec.rb` runs `/app/bin/test` with a fake `docker` first on `PATH`, through feature 26's `spec/support/script_helpers.rb`. The fake logs the arguments of each call, prints one line for each `compose run` (standing for the check's own output), and ends with the status the example gives: for `info`, and for each `compose run` whose argument line matches a pattern the example gives. The examples compare the log with the exact commands, so no real check runs inside the suite. The backend image has no `docker` command, which is the "not installed" case.
  - **`-e TZ=UTC` on the plain run's RSpec and Vitest** makes "UTC only" (question 8) hold even when a `.env` or a later change sets another zone. The commands the README gives for one check stay without it; the containers are in UTC by default.
  - **No heading between checks.** Question 7 shows each check's own output, then the summary, which names each check.
  - **WebMock, not a guard of our own, for the backend.** It covers the HTTP clients the backend uses: OmniAuth's OAuth2 client goes through Faraday and `Net::HTTP`. A probe on 2026-11-09 installed webmock 3.34.0 in a throwaway container of the backend image (Ruby 4.0.9): it refused `GET http://192.0.2.1/` with `WebMock::NetConnectNotAllowedError`, whose superclass is `Exception`, and let a request to `localhost` through. Because it is not a `StandardError`, code that rescues `StandardError` (the app's, Faraday's, OmniAuth's) does not swallow it, and the test fails. A raw socket (`TCPSocket`) is not covered, and the app opens none; the README's Known limitations and conventions.md say what each guard covers.
  - **The probe address is 192.0.2.1** (TEST-NET-1, reserved for documentation), so even a red run, before a guard exists, reaches no real host. The red runs fail fast: `open_timeout: 2` in Ruby, `AbortSignal.timeout(1000)` in the browser tests.
  - **Plain assignment, not `vi.stubGlobal`, for the guards.** Every test file that stubs `fetch` calls `vi.unstubAllGlobals()` after each test, which restores what was there before its stub: the guard. A guard set with `vi.stubGlobal` would be removed by that call.
  - **WebMock changes the shared bundle volume.** The entrypoint installs the gem on the next backend command of every agent. The Build step says so in its report.
  - **Where `bin/test` runs for real.** Its RSpec uses the default test database, `backend/storage/test.sqlite3`, which the Stop hook's RSpec in the main tree also uses. So a real run (item 14, and the Test plan) happens in a copy of the tree under a Compose project of its own, never in the main tree.
  - **A test of another feature that fails in a zone.** Question 5 binds the tests of features 12 to 20. If item 14 finds one, fixing its time is added here as an item and recorded under Deviations with the test's name (owner's standing instruction).
  - **Scenarios with no new code.** "Each check can still run on its own" and "One test by name" are Compose, RSpec, and Vitest commands that already work. "The tests need no credentials" is feature 01's placeholder credentials and OmniAuth test mode; the backend guard makes sure that a test could not reach a provider, and item 14 runs everything with no `.env`. The Test plan walks them. "The README documents the tests" is accepted by `## Docs`.
