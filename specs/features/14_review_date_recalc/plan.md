## Approach

- Data: no change. The review writes feature 12's `notes.next_review_date` together with `notes.last_reviewed_date` (feature 13).
- API: `POST /api/notes/:id/review` (feature 13). Its 200 answer `{ "note": <detail> }` now carries the recalculated `next_review_date` together with the new `last_reviewed_date` (spec edge case):
  - The next review date is the user's today plus the interval the note has at the review: daily +1 day, weekly +7 days, monthly +1 calendar month (the same day number, or that month's last day), custom + its number of days (spec question 1; requirements.md 3.5; feature 12 question 6).
  - It counts from the review day, never from the old date: an overdue note does not catch up, and an early review counts from the day it is made. A monthly note drifts: Jan 31 → Feb 28 → Mar 28 (spec questions 1, 2).
  - A note with the interval None keeps no next review date (feature 12 question 11). An archived note gets a new date like any other and stays archived (feature 13 question 1).
  - A second review on the same day gives the same dates again, so nothing is written (feature 13 question 2). A date changed by hand in between is set again to today plus the interval (spec question 1).
  - The request, the errors, and their order are feature 13's (401, 400, 403, 404). A refused request changes neither date.
- WebSocket: none.
- UI: `frontend/src/NoteDetail.tsx`: the review's answer goes to the list through `onChanged`, as archive and restore do. `Notes` replaces the note's entry in its place (`withNote`), so the list shows the new "Next review: …" (feature 12) with no list request (spec scenario "The list shows the new date"; feature 09 questions 1, 2). The detail already shows the answer's note (feature 13) with feature 12's "Next review" row.
- Decisions:
  - `Note#mark_reviewed!` (feature 13) reads `user.today` once, sets `last_reviewed_date` to it and `next_review_date` to `review_date_after(today)`, and keeps `save!(touch: false)`. `review_date_after` is the private method of `Note` that feature 12's `schedule_from_today` uses, so scheduling and reviewing share one calculation, the month-end rule included, and it gives nil for None. The updated date still stays (feature 13's rule, guarded by its item 4).
  - No feature 13 test is replaced. Feature 13's tests give every scheduled note a next review date equal to today plus its interval at the review, so this feature's recalculation gives the same date (feature 13 plan, Decisions). If an AC-13 test still fails because the next review date changed, that assertion encodes the interim rule of feature 13 question 8: replace it with item 2's test, the way feature 11 replaced feature 09's interim assertions, and record the replacement under Deviations.
  - Item 2 is the test that requirements.md 7 asks for ("A user can mark a note as reviewed, and the next review date is recalculated"). Its name starts with both AC IDs, as the README's example and feature 29's proposal (its question 5) have it, so `grep -r "AC-13"` and `grep -r "AC-14"` both find it.
  - Red steps: items 2 (backend) and 13 (frontend). Once item 2 is built, the other backend items and items 12 and 14 are expected to pass at once: item 2 uses feature 12's calculation and feature 13's lookup, checks, and save, and feature 13 already shows the answer in the detail. Each is kept as the guard of its scenario or edge case and recorded under Deviations, with the temporary mutation named in the item that makes it fail.
  - Fixtures give each note an explicit next review date that differs from today plus its interval, or a note due on the day of the review, so a test sees the recalculation.
  - Time in tests, as in features 12 and 13: `before { travel_to Time.utc(2026, 11, 9, 20, 0) }` and `after { travel_back }`; a later `travel_to` or `travel` in a test is called without a block. The month-end and next-year cases are model tests that travel to noon UTC of each day, for a user with no saved zone, so today is that UTC date.
  - New test files: `spec/requests/review_date_recalc_spec.rb`, `spec/models/note_review_recalc_spec.rb`, and `src/ReviewDateRecalc.test.tsx`, which copies the fetch stub of `src/Notes.test.tsx`, as feature 13's tests do.

Each call travels to the given time, creates a note due that day, marks it as reviewed, prints `<last reviewed date> <next review date>`, and rolls everything back:

  ```ruby
  require "active_support/testing/time_helpers"
  include ActiveSupport::Testing::TimeHelpers
  def review_at(time, **schedule)
    u = User.find_by!(display_name: "Ada Lovelace")
    w = u.collections.find_by!(name: "Work")
    ActiveRecord::Base.transaction do
      u.update!(time_zone: nil)
      travel_to(time) do
        n = u.notes.create!(title: "Recalc", body: "B", collection: w, next_review_date: time.to_date, **schedule)
        n.mark_reviewed!
        puts "#{n.reload.last_reviewed_date} #{n.next_review_date}"
      end
      raise ActiveRecord::Rollback
    end
  end
  ```
