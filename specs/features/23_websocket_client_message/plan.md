## Approach

- Data:
  - Table `review_dismissals` (new migration): `user_id` (integer, not null, foreign key to `users`, indexed), `note_id` (integer, not null, foreign key to `notes` with `on_delete: :cascade`), `next_review_date` (date, not null), and the timestamps. A unique index on (`note_id`, `next_review_date`). This is requirements.md 6's "notification acknowledgement" (spec question 2).
  - Model `ReviewDismissal` (`backend/app/models/review_dismissal.rb`): `belongs_to :user`, `belongs_to :note`.
  - `Note` includes a new concern, `ReviewDismissible` (`backend/app/models/concerns/review_dismissible.rb`): `has_many :review_dismissals, dependent: :delete_all`, and `after_update :end_review_dismissals, if: :saved_change_to_next_review_date?`, which deletes the note's dismissals. So a dismissal ends when the note's next review date changes: a review (features 13, 14), a new date in the edit form (feature 12 question 7), or the interval None, which removes the date (feature 12 question 11), and a date that later returns to the dismissed one reminds again (spec question 2; edge cases). An archive, a restore, an interval change that keeps the date, and a second review on the same day change no date, so they keep it. One line in `note.rb`: `include ReviewDismissible`.
- The batch (feature 20's `ReviewReminderBatch`) leaves out a note that has a dismissal for its current next review date: `where.not(ReviewDismissal.where("review_dismissals.note_id = notes.id AND review_dismissals.next_review_date = notes.next_review_date").arel.exists)`, after the `or` of feature 20 (probed on 2026-11-09: `(due today OR overdue) AND NOT EXISTS (...)`, and a dismissal for another date does not hide the note). The date is part of the match, so a dismissal left behind by a direct database write still never hides the note's reminder on another date.
- WebSocket (`ReviewRemindersChannel`, identifier `{"channel":"ReviewRemindersChannel"}`):
  - The message (spec question 1), Action Cable's `message` command with the ack as JSON text in `data`: `{"command":"message","identifier":"{\"channel\":\"ReviewRemindersChannel\"}","data":"{\"action\":\"ack\",\"note_id\":7,\"next_review_date\":\"2026-11-09\"}"}`. No anti-forgery token: only the app's own origin can open the connection (feature 22 question 6). A field other than these three is ignored.
  - `perform_action(data)` (public: Action Cable's connection calls it for every message, and this override replaces Action Cable's "Unable to process" log): a Hash whose `"action"` is `"ack"` goes on to Action Cable's dispatch (`super`), which calls `ack`. Anything else, another action (`"snooze"`), no action, or a payload that is not an object, answers `{ "type": "error", "error": "invalid" }` with `transmit`, and nothing changes (spec question 3). Action Cable counts a public method that a channel defines among its actions, so `perform_action` is listed too; a message with `"action": "perform_action"` reaches this method again and answers `invalid` (probed on 2026-11-09, lane p20).
  - `ack(data)` (public: with `perform_action`, the channel's only actions) runs `ReviewAck.new(user, data).record` (new, `backend/app/models/review_ack.rb`), with the user read again from the database (`User.find(current_user.id)`, as feature 20's batches do):
    - `"invalid"` unless `note_id` is an Integer and `next_review_date` is text that matches `\A\d{4}-\d{2}-\d{2}\z` and names a real date (`Date.valid_date?`), the rule of feature 12's next review date. Action Cable decodes the JSON as it is: `7.0` and `7.5` stay Floats, `"7"` a String, and `true` a boolean (probed). `invalid` is checked before any lookup (spec question 3).
    - `"not_found"` unless the user has a current reminder for it: `user.notes.due_today(today).or(user.notes.overdue(today)).find_by(id: note_id, next_review_date: date)`, with `today = user.today`. Another user's note, a deleted or unknown note, an archived note, a note with the interval None, a later note, and a date that is not the note's next review date all answer the same (spec question 3; feature 21 question 1). Whether the reminder is already dismissed does not matter.
    - Otherwise `ReviewDismissal.create_or_find_by!(user:, note:, next_review_date:)` and `nil`. A second ack for the same reminder, from another tab at the same moment included, finds the row the first one made, through the unique index (spec scenario "The same ack twice").
    - An error code: `transmit({ type: "error", error: code })` to the sender, nothing recorded, and the connection stays open. Accepted: no answer to the sender, then `ReviewRemindersChannel.send_batch_to(user)` (feature 20), so each open connection of the user receives a new batch without the reminder (spec question 2; feature 20 question 5).
  - A message whose `data` is not JSON text: Action Cable decodes a `message` command's `data` before any channel sees it (`Subscriptions#perform_action`), and when the decoding fails, it only logs the error and answers nothing. So `ApplicationCable::Connection` (feature 22's connection) overrides `handle_channel_command(payload)` (public, as in Action Cable): a `message` command whose `data` is missing or is not JSON text goes on with `data` `"null"`, so the channel's `perform_action` receives `nil` and answers `invalid` (spec question 3: "a message that is not a well-formed ack"). Every other command goes on unchanged. The override calls `super`, so feature 22's `before_command` still checks the sign-in before anything else. A frame that is not JSON at all is not a command, and stays Action Cable's (probed on 2026-11-09, lane p20, resumed run: the rewrite, and the refusal once the sign-in is gone).
  - Before each message, so before each ack, feature 22's `before_command` checks that the connection's sign-in still exists, and closes the connection when it does not (feature 22 question 5).
- UI:
  - `frontend/src/cable.ts`: the `Cable` object gains `perform(action, data)`. While the socket is open it sends the `message` command above, with `data` the JSON text of `{ action, ...data }`, and returns true; otherwise it sends nothing and returns false.
  - `frontend/src/ReviewReminders.tsx` (feature 20's panel): "Dismiss" calls `cable.perform('ack', { note_id, next_review_date })` with the reminder's values as the batch gave them, takes the reminder out of the list at once, without waiting for any answer, and moves the focus to the heading "Review reminders" (`tabIndex={-1}`, feature 20). When `perform` returns false (the socket closed a moment before the panel heard of it), nothing was sent, so the reminder stays, and the offline state follows with the close (spec question 5: no ack is lost unseen). No confirmation, no undo, and no busy state (spec question 4). With no reminder left, the panel shows "No review reminders". An `{ "type": "error" }` message shows nothing, and the next batch replaces the list as always, so a reminder whose ack was not recorded and that is still current shows again (spec question 5). While the panel is offline, "Dismiss" is disabled (feature 20), so no ack is sent then.
  - The notes list, the detail, and the "Review" filter do not change: a dismissed note keeps its "Due today" or "Overdue" (spec question 4; features 15, 16).
- Decisions:
  - **A table of its own, not a column on `notes`.** requirements.md 6 names a "notification acknowledgement", and the row keeps who dismissed which note for which date. `user_id` is the note's user; it makes the ownership explicit, as requirements.md 5 asks for acknowledgements.
  - **The dismissal ends through a callback on the note**, so every path that saves a note ends it: the API, feature 13's review (`save!(touch: false)` still runs callbacks), and `update!` in a runner. `update_columns` skips callbacks, so the walkthrough changes dates with `update!` wherever a dismissal is involved. The callback lives in this feature's concern; lane A's `note.rb` gets one `include` line.
  - **The rules of an ack live in `ReviewAck`**, a plain class like feature 15's `NoteListFilter`, so the channel stays thin. Channel specs drive it with `perform :ack, note_id: ..., next_review_date: ...`, which goes through `perform_action` (Action Cable's `ChannelTestCase#perform` adds the action to the data and calls it; probed).
  - **Time in tests**, as in feature 20: `travel_to Time.utc(2026, 11, 9, 20, 0)`; midnight cases travel to 23:59:30 and then 00:00:30 UTC for a user with no saved zone; later `travel_to` calls without a block. A check's batch is made by running the channel's periodic timer callback on the subscription (`subscription.instance_exec(&callback)`, feature 20), never by sleeping. The frontend computes no date.
  - **Channel specs compare with string keys**, as in feature 20: `transmissions` hold each message with indifferent access, so an error answer is compared as `{ "type" => "error", "error" => "invalid" }`, and a batch with `deep_stringify_keys`.
  - **requirements.md 7** asks for the test "WebSocket client → server message affects server behavior": item 7, with item 8 (the batches sent after the ack).
  - **New test files**, so the earlier ones keep their assertions: `spec/channels/review_reminders_ack_spec.rb`, `spec/channels/review_reminders_message_spec.rb` (the connection's override, `RSpec.describe ApplicationCable::Connection, type: :channel`, with `subscriptions` and `close` stubbed as in feature 22's item 8), `spec/models/review_dismissal_spec.rb`, `spec/requests/review_dismissals_spec.rb`, `src/cable.perform.test.ts`, and `src/ReviewRemindersDismiss.test.tsx`. Each spec file names its type. The frontend tests drive feature 22's fake socket as feature 20's tests do, and read what the app sent in `socket.sent`.
  - **The existing files this feature changes, and nothing else:**
    - shared with lane A: `backend/app/models/note.rb` (one line, `include ReviewDismissible`) and `backend/db/schema.rb` (regenerated by `db:migrate`, never edited by hand; it keeps lane A's tables and columns);
    - lane B's own, from features 20 and 22: `backend/app/channels/review_reminders_channel.rb`, `backend/app/channels/application_cable/connection.rb` (the `handle_channel_command` override), `backend/app/models/review_reminder_batch.rb`, `frontend/src/cable.ts`, and `frontend/src/ReviewReminders.tsx`.
    - New: the migration, `backend/app/models/review_dismissal.rb`, `backend/app/models/review_ack.rb`, `backend/app/models/concerns/review_dismissible.rb`, and the six test files above. No change to the controllers, `routes.rb`, or `src/test/`.
  - Pipelined run: features 13 to 16, 20, and 22 come before this one. If one is not Done when this Build starts, Build records that under Deviations (owner's standing instruction).

## Test plan

Walkthrough for Verify, against the running app, with the Verify harness as in feature 20's Test plan (the slot the orchestrator assigns), whose shorthands this plan reuses: **watch**, **the panel**, **the entry of X**, **Data**, **Waiting for a check**, **Midnight**, and **Losing the connection** (with its modes "pass", "hold", "release", and "silent").
