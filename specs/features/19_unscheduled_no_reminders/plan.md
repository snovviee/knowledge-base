## Approach

- Data, API, WebSocket, UI: no change expected. This feature adds tests and documents.
- Where the rule already lives (spec question 1). Features 15 and 16 define "due today" and "overdue" only for notes whose interval is not None, in one place in `Note` (planner notes): `Note#review_state(today)` gives nil for a note with the interval `none`, and `Note.due_today(today)` and `Note.overdue(today)` both build on `Note.scheduled` (interval not `none`). Feature 12 also removes the next review date of a note set to None before every save (`drop_unused_schedule_values`, feature 12 question 11), so such a note has no date to be due on. Every kind of review reminder calls them:
  - the notes view: `review_state` in every note of the notes API, which the list's and the detail's "Due today" and "Overdue" labels show (features 15, 16); the "Review" filter's `due_today` and `overdue`, and its `unscheduled` (`Note.unscheduled`, feature 17), the one choice that lists these notes; the list's "No review scheduled" and the detail's "Review interval: None" and "Next review: Not set" (feature 12 questions 14, 16);
  - the WebSocket: feature 20's batch (`ReviewReminderBatch`, `user.notes.due_today(today).or(user.notes.overdue(today))`), and so the "Review reminders" panel; feature 23's ack, which accepts only a current reminder (`ReviewAck`), and its dismissals, which end when the note's next review date changes, the None that removes it included (`ReviewDismissible`).
- A schedule set again (spec question 2). An edit that sets an interval other than None with no date gets the user's today plus the interval (feature 12 question 8, `schedule_from_today`); one with a date keeps that date, a past one included (feature 12 questions 7, 10). Feature 20 sends a batch right after the save, so a date of today or earlier is reminded at once, and a later date when it comes. Marking a note with the interval None as reviewed sets its last reviewed date and leaves it with no next review date (features 13, 14).
- Decisions:
  - **Every item is a guard**, as in feature 18. Each test is expected to pass when it is written, because features 12 to 17, 20, and 23 already hold the behavior. Build proves that each one can fail with the temporary mutation that its item names (a mutated copy mounted over the one file in a single `docker compose run`, as feature 22's Build did, or a change reverted at once), and records each under Deviations (owner's standing instruction; brief, Build). A test that fails for the right reason shows a real gap: Build writes the least code that makes it pass, in the file the gap belongs to, and records that under Deviations.
  - **A stray date makes the interval rule testable.** No path of the app gives a note with the interval None a next review date: feature 12 drops it before every save. So with notes made through the app alone, dropping `Note.scheduled` from the scopes would change nothing, and no guard could fail. The model and channel guards therefore also hold notes with the interval None whose row has a next review date written straight to the database (`update_columns`, which skips feature 12's rule), dated before, on, and after today. requirements.md 3.5 makes "due" need an interval other than None whatever the date, and these rows show that the interval, not the missing date, keeps such a note out (spec question 1; edge case "No review schedule means the interval None").
  - **No browser test.** The UI shows the server's states and the filter's answers. Its texts for a note with no schedule are feature 12's ("No review scheduled", "Review interval: None", "Next review: Not set"), with its tests (`AC-12 the list shows the next review date, or No review scheduled`, `AC-12 the detail shows the review interval and the next review date`); its labels come from `review_state` alone (features 15, 16, whose tests show that a null state shows no label); and the "No review scheduled" choice and its address are feature 17's. A note with the interval None has no next review date in any answer, so no change to the browser code that a real answer can meet would make a browser guard fail. The Test plan checks the screens.
  - **"On its date" without waiting**, as in feature 18: a check's batch is `ReviewReminderBatch.for(user)` at that moment (feature 20), so a request spec reads it after `travel_to` the date. A check itself is run with the channel's periodic timer callback (`subscription.instance_exec(&callback)`, feature 20), never by sleeping.
  - Time in tests, as in features 12 to 20: `travel_to Time.utc(2026, 11, 9, 20, 0)` for a user with no saved zone, so today is 2026-11-09; midnight cases travel to 23:59:30 and then 00:00:30 UTC. A later `travel_to` in a test is called without a block. The frontend is not tested here.
  - Channel specs, as in features 20 and 23: the connection is `stub_signed_in_connection` (feature 22's `spec/support/cable_helpers.rb`); `transmissions` are compared with string keys (`deep_stringify_keys`); a broadcast with `have_broadcasted_to(user).from_channel(ReviewRemindersChannel)`. A dismissal in a request spec is a `ReviewDismissal` row, as feature 23's ack makes it.
  - **requirements.md 3.7 and 11** ask that notes without a review schedule generate no notifications. Item 2's test carries that wording, as feature 18's item 2 does for archived notes. requirements.md 7 names no test for this case.
  - **New test files**, and no change to any other file: `spec/models/unscheduled_reminders_spec.rb`, `spec/requests/unscheduled_reminders_spec.rb`, and `spec/channels/unscheduled_reminders_spec.rb`. A test that fails for the right reason changes the one production file the gap belongs to, named under Deviations.
  - Pipelined run: this feature is built after features 17, 20, 23, and 18 (build order), by whichever lane is free. If a feature it depends on is not Done when this Build starts, Build records that under Deviations (owner's standing instruction).
