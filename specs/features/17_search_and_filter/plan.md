## Approach

- Data:
  - `notes.search_title` (string), `notes.search_body` (text), and `notes.search_source_url` (string, null): the search copies. Each is its field in Unicode NFC, case-folded (`downcase(:fold)`), with each run of whitespace made one space and the ends trimmed. `search_source_url` is null for a note with no source URL (spec questions 4, 13).
  - They are set before every save of a note, so every path that saves one keeps them: the API, feature 13's review (`save!(touch: false)`), and `bin/rails runner`. A value equal to the stored one is not written, so a review still keeps `updated_at`.
  - One migration adds them and fills them for the notes that exist, with its own copy of the rule. No index: the match uses `instr`, which no index serves, and it runs over one user's notes (index on `user_id, created_at`).
- Review states, in `Note` beside features 15 and 16's `due_today` and `overdue`:
  - `Note.due_next_7_days(today)` → `Note.active.scheduled` with a next review date from `today + 1` through `today + 7` (spec question 7). It never shares a note with `due_today(today)` or `overdue(today)`.
  - `Note.unscheduled` → the notes with the interval `none`, in any status (spec question 8).
- Search: `Note.fold_for_search(text)` is the one folding rule, used for the copies and for the search text. `Note.matching(text)` folds the text and keeps a note when `instr(search_title, text) > 0`, `instr(search_body, text) > 0`, or `instr(search_source_url, text) > 0`. `instr` takes the text as it is, so `%`, `_`, `*`, `\`, and quotes match as themselves (spec question 6), and each field is searched on its own (spec edge case).
- API: `GET /api/notes` (JSON under `/api`, as in [docs/api_contract.md](../../docs/api_contract.md)) takes these query parameters, each optional. A parameter left out or `""` does not filter (spec question 12):
  - `search`: text, tidied as the copies are (ends trimmed, each run of whitespace one space). Empty after tidying: no search (spec question 13). More than 2,000 characters after tidying: `too_long` (spec questions 6, 13). Not text (`search[]=rails`, `search[a]=b`): `invalid` (spec question 18).
  - `collection_id`: one collection's id, a whole number written in digits. The answer has the notes in that collection. Another user's collection, a deleted one, or a value that is not a whole number (`abc`, `1.5`): 200 `{ "notes": [] }` (spec question 9).
  - `tag_id`: one tag's id, the same way: the notes that have that tag; anything else: 200 `{ "notes": [] }` (spec question 9).
  - `status`: `active` or `archived`. Any other value, another letter case included (`Active`): `invalid` (spec questions 9, 12).
  - `review`: `due_today` (feature 15), `overdue` (feature 16), `next_7_days`, or `unscheduled`. Any other value: `invalid`.
  - All of them combine (AND), and the answer stays newest first (spec question 2).
  - A refusal is 422 `{ "error": "validation_failed", "fields": { ... } }`, naming in one answer every parameter that breaks a rule: `search`, `status`, `review` (spec questions 9, 12; feature 09 question 8). No sign-in: 401 first, whatever the parameters.
- WebSocket: none.
- UI:
  - `frontend/src/NoteFilters.tsx` (feature 15's filter bar) holds, in this order: "Search", an `<input type="search">` labelled "Search", empty at first, with `maxLength={2000}` (spec questions 15, 17); then the selects "Collection", "Tag", "Status" ("All", "Active", "Archived"), and "Review" ("All", "Due today", "Overdue", "Next 7 days", "No review scheduled"), each labelled by a `<label>` and starting at "All" (value `""`) (spec questions 1, 15). The bar shows only with the list, as in feature 15.
  - The "Collection" and "Tag" choices are "All" and then the left area's collections or tags, in its order (spec questions 10, 16). `frontend/src/NameListArea.tsx` gains an optional prop `onRecords(records | null)`, which it calls whenever its list changes: the records once loaded and after a create, a rename, or a delete, and null while it loads or has failed. `Collections.tsx` and `Tags.tsx` pass it on; `App` keeps the two lists and gives them to `Notes`. So a create, a rename, a delete, or a "Try again" that succeeds in the left area reaches the choices at once, and they offer only "All" until the lists load.
  - A chosen collection or tag that the left area's list no longer has (it was deleted) counts as "All": the select shows "All", and the list address leaves it out, so the list loads again (spec question 10). A renamed one keeps its id, so it stays chosen with its new name.
  - Typing in "Search": 300 ms after the last change, the field's text, tidied as the server tidies it, becomes the search of the list address. A text that is empty after tidying leaves `search` out (spec questions 5, 13). A choice in a select, and "Clear search and filters", change the address at once (spec edge case).
  - `notesAddress` (feature 15) writes the parameters in this order: `search`, `collection_id`, `tag_id`, `status`, `review`, and leaves out each one that is empty or at "All". With "Review" alone set, the address is the one of features 15 and 16, such as `/api/notes?review=due_today`.
  - Loading, the load error with "Try again", the 401, and only the latest answer are feature 15's, keyed on the address, so they hold for the search and every filter (spec question 14).
  - Empty states, chosen from the search and the filters that the shown answer was asked with (spec question 11):
    - nothing set: "No notes yet" (feature 09);
    - only "Review" set: its own message, with no button: "No notes are due for review today." (feature 15), "No notes are overdue for review." (feature 16), "No notes are due for review in the next 7 days.", or "Every note has a review schedule.";
    - anything else set (a search, a collection, a tag, or a status, with or without a review choice): "No notes match your search and filters." with the button "Clear search and filters". The button empties "Search", sets every filter to "All", and loads the list at once with `GET /api/notes`.
  - The search and the filters keep their values while a note or a form is open, and a reload resets them (spec question 3): they are state in `Notes`, kept neither in the page address nor in browser storage.
- Decisions:
  - Stored, folded copies, as `folded_name` for names (feature 06): SQLite's `LIKE` and `LOWER` fold only ASCII letters (spec, Notes for Plan; SQLite 3.54.1). The fold is NFC and then `downcase(:fold)`, as `UniquelyNamed` folds names, then `squish`.
  - `NoteListFilter` (feature 15) gains `search`, `collection_id`, `tag_id`, and `status`, and the `review` values `next_7_days` and `unscheduled`. Its validations add `too_long` or `invalid` on `search`, and `invalid` on `status` and `review`, so one 422 names every parameter that breaks a rule. `collection_id` and `tag_id` never fail: a value that is not one of the user's finds no note, so an answer never tells whether another user's collection or tag exists. The tag filter keeps the user's notes whose id is among `NoteTag.where(tag_id: <id>).select(:note_id)`.
  - Frontend timing. The pause is an effect on the field's text that sets the search 300 ms later, in a timer callback, so no state is set synchronously inside an effect (`react-hooks/set-state-in-effect`). The collection and tag that count are derived at render from the left area's lists, so a deleted choice needs no effect that sets state. The browser tidies the search before it sends it, as the server does, so a text of only spaces asks for nothing new.
  - Features 15 and 16's tests stay as they are: they check only the first choices of "Review", use unknown values no feature adds (`soon`, `late`), and assert exact addresses only with "Review" alone set, which this feature keeps.
  - Other earlier tests: the bar shows only with the list. The AC-09 to AC-11 tests that look for "Work", "Books", or "Archived" anywhere in the notes area do it in a detail, where the bar is hidden, or within one entry, and feature 12's test finds "No review scheduled" through each entry's `note-review` element. The left area makes no new request: the choices reuse its lists, so the order of `GET /api/collections` requests that `src/NoteMove.test.tsx` relies on (`collectionsForForm`) is unchanged. If an earlier test still meets a choice's text, that query is scoped to its entry or detail, and the change is recorded under Deviations, as feature 11 did with feature 09's assertions.
  - Unscoped queries: the bar has no status, no alert, no list, and no list item, and "Clear search and filters" shows only in its empty state. "Collection" is also the note form's label, and "No review scheduled", "Due today", and "Overdue" are also the list's texts, so AC-17 tests find the controls with `within(area).getByRole('combobox', { name: ... })` or `getByRole('searchbox', { name: 'Search' })`, and the list's texts within an entry.
  - Time in tests. Backend tests fix the time with `travel_to Time.utc(2026, 11, 9, 20, 0)`, as features 12 to 16 do. The frontend computes no date. The tests of the pause fake only `setTimeout` and `clearTimeout` (`vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout'] })`), give `advanceTimers: vi.advanceTimersByTime` to `userEvent.setup`, and move time with `vi.advanceTimersByTimeAsync`; Testing Library's `findBy` keeps polling with the real `setInterval`. The other search tests use real timers: the 300 ms pause is within `findBy`'s 1 s.
  - New test files, so the earlier ones keep their assertions: `spec/models/note_search_spec.rb`, `spec/requests/note_search_spec.rb`, `spec/requests/note_filters_spec.rb`, `src/NoteSearch.test.tsx`, and `src/NoteFilters.test.tsx`. The frontend files copy the stub and the fixtures of `src/ReviewDueToday.test.tsx` (feature 15), with collections and tags.
  - Pipelined run: features 15 and 16 come right before this one. If one is not Done when this Build starts, Build records that under Deviations (owner's standing instruction).
