## Approach

- Data, API, WebSocket: no change. Opening and closing a panel, and a change of width, send no request (spec questions 6, 10).
- Narrow or wide (spec question 1): `frontend/src/useNarrowScreen.ts` (new) is a hook over `window.matchMedia('(width < 768px)')`, read with `useSyncExternalStore`, so a change of width re-renders at once (spec question 10). True below 768 CSS pixels. The range syntax makes a fractional width such as 767.5 px narrow, which `(max-width: 767px)` would not.
- UI, `frontend/src/App.tsx`, the main layout. One tree for both widths, so nothing is unmounted when the width changes or a panel opens or closes: the collections and tags areas keep their lists, their open forms, what was typed, and their confirmations (spec questions 4, 10). From top to bottom:
  - The header (spec question 5): it wraps (`flex-wrap`, with a small row gap). The display name is cut with "…" (`min-w-0 truncate`, and its container `min-w-0`), and "Log out" never shrinks (`shrink-0`). "Could not log out. Try again." stays under the header, across the full width, as now.
  - The bar, shown only while narrow, right under the header (and under the logout alert when it shows): the buttons "Collections" and "Menu", each with `aria-expanded` `"true"` or `"false"` (spec questions 3, 4). They follow feature 24: the outlined kind (`rounded border border-slate-300 px-3 py-1 text-sm`), a hover state (`hover:bg-slate-100`), a focus ring (`focus:outline-none focus:ring-2 focus:ring-slate-300`), and the header's side padding (`px-4`) (spec edge case).
  - The left area: the same element at both widths, holding `Collections` and then `Tags`. Wide: the left column, as now (`w-64 shrink-0 border-r`). Narrow: across the full width, below the bar and above the main area, each area in its own panel; a panel that is not open has the `hidden` attribute, so it is neither seen nor reached with Tab, and stays mounted. With no panel open, the left area itself is `hidden`, so no empty border shows.
  - The main area: the reminders panel of feature 20 at its top, then the notes area, as on a wide screen; never inside a panel of the bar (spec question 7). It gets `min-w-0`, so long content wraps inside it instead of widening the page.
  - The row that holds the left area and the main area is a row when wide (`flex`) and a column when narrow (`flex flex-col`). So an open panel pushes the reminders panel and the notes down (spec question 4).
  - Panels: one state in `App`, the open panel: `'collections'`, `'menu'`, or none. A bar button opens its panel, which closes the other, or closes its own panel when it is open (spec question 4). Nothing else changes it: not Escape, not a choice outside the panel, only a change of width. When the window turns narrow, the open panel is reset to none (spec question 10).
- UI, other files:
  - The filter bar of feature 17 (`frontend/src/NoteFilters.tsx`): `flex flex-wrap` at every width, so it wraps when its controls do not fit, at 768 px too (spec question 8). While narrow, the "Search" control takes a line of its own (`basis-full`, the field `w-full`). "Collection", "Tag", "Status", and "Review" follow in that order, each with its label, and each label and select kept together (`shrink-0`). `Notes` passes `narrow` to the bar, or the bar reads `useNarrowScreen` itself.
  - Long words (spec question 9): every text that holds a user's words breaks inside its line: titles in the list and the detail, collection and tag names in the areas, the list, and the reminders panel, the review line, the body, and the source URL (`wrap-anywhere`, Tailwind 4's `overflow-wrap: anywhere`, which also lets a flex item shrink below the width of its longest word). A flex item that holds such a text gets `min-w-0`.
  - Rows of buttons wrap (`flex-wrap`): the detail's actions (already), the note forms' "Create" or "Save" and "Cancel", the delete confirmations' "Delete" and "Cancel", the name forms' buttons, and the reminders' "Open" and "Dismiss".
  - The note forms and the detail take the full width of the notes area (`w-full`; the form keeps `max-w-2xl`, which only limits a wide screen), and each field the full width of the form (spec question 9). The notes list stays one column at every width (feature 09).
  - The reminders panel (feature 20): its list scrolls inside it (`overflow-y-auto`) and is at most 16rem (256 px) high, so at 320 × 568 px, with the header on two lines and the bar, the heading "Notes" shows on the first screen (spec question 7). If feature 20 already bounds the list at 16rem or less, it stays as built.
- Decisions:
  - **No `md:` classes.** The hook decides the layout, and the classes are plain. Tailwind's breakpoints are in rem, so they move with the browser's font size, and jsdom applies no media query, so tests could not see them. With the hook, the tests see the same classes as the browser for each width.
  - **Hidden, never unmounted.** A closed panel and the left column are the same mounted areas with `hidden` or other classes. Rendering two trees, one per width, would remount the areas: their lists would load again, and a typed name would be lost (spec questions 4, 6, 10).
  - **The reset at turning narrow.** `App` keeps, next to the open panel, the width it was opened at, and resets the panel while rendering when the hook's value changed (React's pattern for state from the previous render). This avoids a state change inside an effect, which the lint rule `react-hooks/set-state-in-effect` flags. The pattern (`if (narrow !== narrowBefore) { setNarrowBefore(narrow); if (narrow) setPanel(null) }` during render, beside `useSyncExternalStore` over `matchMedia`) passes the project's ESLint, probed on 2026-11-09 with `npx eslint --stdin` in the frontend container (lane p24), where an effect that sets state was flagged.
  - **The bar's buttons are outlined buttons** (feature 24's kinds): they open and close, as "Edit" or "Cancel" act, and plain buttons ("New note") open a form.
  - **Tests.** jsdom has no `matchMedia` and no layout. A [SETUP] stub of `matchMedia` is assigned in `src/test/setup.ts` (wide, 1280 px, by default), not stubbed with `vi.stubGlobal`, because most test files call `vi.unstubAllGlobals()` (as for the fake WebSocket of feature 22). `setWindowWidth(px)` in `frontend/src/test/screen.ts` changes the width and fires `change` on each query whose answer changes, inside `act`. Every earlier test renders at 1280 px, so it sees the wide layout it was written for.
  - **What Vitest checks, and what only Verify can.** Vitest checks the bar, the panels, `aria-expanded`, `hidden`, the order of the areas in the page, the requests, what stays typed, Escape and Tab, and the classes that make the layout fit (`truncate`, `shrink-0`, `flex-wrap`, `basis-full`, `wrap-anywhere`, `min-w-0`, `w-full`, the list's height and scrolling), with the helpers of feature 24 (`src/test/ui.ts`). Only a real browser can check that nothing scrolls sideways, that a long word breaks, that a name is cut with "…", that "Notes" shows on the first screen at 320 × 568, and where things are drawn. The Verify walkthrough does it with Playwright's viewport sizes from the spec: 320 × 800, 320 × 568, 375 × 667, 375 × 800, 767 × 800, 768 × 800, and 1280 × 800, comparing `document.documentElement.scrollWidth` with `window.innerWidth`.
  - **Scoped queries.** The button "Collections" and the area's heading "Collections" have the same text, and so do "Collection" in the filter bar and in the note form: tests find them by role and within their area (spec, Notes for Plan).
  - **Test file:** `src/ResponsiveLayout.test.tsx` (new), which copies the fetch stub of feature 17's `src/NoteFilters.test.tsx` and drives the fake WebSocket as feature 20's tests do.
