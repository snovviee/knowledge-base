## Approach

- Data, API, WebSocket: no change. Every state this feature checks is drawn by the browser from answers and messages that features 01 to 23 define.
- UI:
  - **A screen that fails to draw (spec question 2).** `frontend/src/PageError.tsx` (new) holds `PageErrorBoundary`, a React error boundary (a class component with `static getDerivedStateFromError`). Until a part of the page throws while it is drawn, it renders its children. After that it renders only a full-page screen: `<main>` with the alert "Something went wrong. Reload the page." (`role="alert"`) and the button "Reload page", in the look of the other full-page screens (the server error's centered column, its red text and its filled button). "Reload page" calls `reloadPage()` from `frontend/src/reloadPage.ts` (new: `window.location.reload()`). The reloaded page checks the session as every page load does (feature 04).
  - `frontend/src/App.tsx`: the component that is `App` today keeps its code under another name, and the default export `App` renders it inside `PageErrorBoundary`. So the boundary holds the whole page, and every test that renders `<App />` has it. `main.tsx` does not change.
  - A failed request keeps its own message in its own place, as features 01 to 23 built it: an error boundary catches only errors thrown while drawing, never a rejected `fetch` or an error answer (spec question 2; edge case "A failed request keeps its own message").
  - **Hover states (spec questions 3, 5).** A hover state is a `hover:` class that changes the background, the border, the text color, or the underline. Added where none is today:
    - "Continue with Google", "Continue with GitHub", and the server error's "Try again" (`App.tsx`): `hover:bg-slate-700`, as every other dark filled button.
    - The name field of the collections and tags forms (`NameListArea.tsx`) and every field of the note forms (`fieldClass` in `NoteForm.tsx`: "Title", "Body", "Source URL (optional)", the "Collection" select, "Review interval", "Number of days", and "Next review date (optional)"): `hover:border-slate-400 hover:bg-slate-50`. The background keeps a visible change on a field marked invalid, whose red border (`aria-invalid:border-red-600`) wins over the hover border.
    - Each checkbox of the "Tags" group (`NoteTags.tsx`): its row, the `<label>` that holds the checkbox and the tag's name, gets `rounded hover:bg-slate-100`. A native checkbox draws its own box, so the change shows on the row around it.
    - Any element that features 11 to 23 added with no hover state gets the same treatment by its kind: a field `hover:border-slate-400 hover:bg-slate-50`, a button the hover of its kind (see the kinds below). Item 6's sweep names each one.
  - **Focus states (spec question 5).** No change is expected: every interactive element either keeps the browser's own focus outline or replaces it with a ring (`focus:ring-2 focus:ring-slate-300`). An element that removes the outline (`focus:outline-none`) without a ring in its place would get `focus:ring-2 focus:ring-slate-300`. The elements that only the app moves the focus to (`tabIndex={-1}`: a note's title in its detail, the "Tags" group, the heading "Review reminders") stay without a ring.
  - **One look per kind (spec question 4).** The looks below are the ones features 01 to 10 built. An element of a kind with another look is changed to the kind's look.

    | Kind | Look (Tailwind classes) | Elements |
    |---|---|---|
    | Font family | the default sans family; no `font-mono` or `font-serif` | every screen |
    | Area heading | `font-semibold`, the base size (16 px) | "Collections", "Tags", "Review reminders", "Notes" |
    | View heading | `text-lg font-semibold` | a note's title in its detail, "New note", "Edit note" |

    | Red | `text-red-700` | alerts of the main layout |
    | Filled button | `rounded px-3 py-1 text-sm text-white`, with `bg-slate-900`, or `bg-red-700` for a delete | "Create", "Save", "Try again" in the main layout, the "Delete" that confirms a delete |

    Every button of the main layout is of one of the four button kinds, except the notes' titles in the list, which read as the entries' text (they keep `hover:underline`). The buttons that features 13 to 23 added keep their look if it is one of the four kinds. One that has another look takes the kind of its neighbors: "Mark as reviewed", among the detail's actions, is outlined; "Clear search and filters", alone under an empty state like "New note", is plain; "Open" and "Dismiss", the actions of a reminder's row, are row actions.
    The labels inside an entry or a detail ("Archived", and features 15 and 16's "Due today" and "Overdue") and the detail's "Marked as reviewed." (feature 13, a status in `text-green-700`) are of none of these kinds: spec question 4 names no such kind, so they keep their own look, and the sweeps leave them out. So do the delete confirmation's question and the tags area's "Notes with this tag are kept.", which are neither entries nor alerts.
    Two elements of features 06 to 09 differ from their kind today, and are changed: the alert of the collections and tags delete confirmation (`NameListArea.tsx`, `text-xs`, becomes `text-sm`), and the new-note form's "Create a collection first. Every note belongs to a collection." (`NoteForm.tsx`, an empty state in `text-slate-700`, becomes `text-slate-600`). Item 7's sweep names any other.
  - **Light theme only.** No change: no class uses the `dark:` variant, no style reads `prefers-color-scheme`, and nothing sets `color-scheme`, so the browser draws the page and its controls in their light look whatever the system theme. Item 9 guards it.
- Decisions:
  - **jsdom applies no CSS.** The Vitest tests read the Tailwind classes, through helpers in `frontend/src/test/ui.ts` (item 1). The Verify walkthrough checks the real look in Chromium: computed styles, Playwright's hover, the Tab key, and a dark color scheme.
  - **The render-failure trigger** is a notes list answer whose note has `"collection": null`. The list reads the collection's name while it draws, so the draw throws. The test uses it through the fetch stub, and the walkthrough through `kb.block` with a 200 answer. No component is mocked for it.
  - **`reloadPage` is a module of its own**, so the test can replace it with `vi.mock('./reloadPage')`: jsdom cannot reload, and its `window.location.reload` cannot be spied on. The boundary's test is in its own file, because `vi.mock` applies to a whole file. React reports an error that a boundary caught with `console.error`; that test silences it with `vi.spyOn(console, 'error').mockImplementation(() => {})`.
  - **One class component.** React's error boundaries must be classes. The boundary has no parameter properties and no enum, so it passes `erasableSyntaxOnly` in `tsconfig.app.json`. A class with `state` and `static getDerivedStateFromError` passes the project's ESLint (the recommended rules of `eslint-plugin-react-hooks` 7.1.1, and `react-refresh`), probed on 2026-11-09 with `npx eslint --stdin` in the frontend container (lane p24).
  - **Guards.** Most scenarios are states that features 01 to 23 built and test under their own AC IDs. This feature checks them across the app with AC-24 tests (spec question 1), so that `grep -r "AC-24"` finds each scenario. Those tests are expected to pass at once. Each is kept as the guard of its scenarios and recorded under Deviations, with the temporary mutation that its item names, which makes it fail. Items 2, 4, 5, and 7 are the red steps; item 6 is red when an element of features 11 to 23 has no hover state, and a guard otherwise.
  - **Lists of elements, not loops of tests.** The sweeps (items 6 to 8) walk the screens inside one test each and name every element that breaks the rule in the failure message. Test names stay plain string literals (feature 29).
  - **Test files.** `src/PageError.test.tsx` (the boundary), `src/UiQuality.test.tsx` (hover, focus, the kinds, light theme), and `src/UiStates.test.tsx` (the guards of the empty, loading, busy, validation, and error states). They copy the fetch stub of feature 17's `src/NoteFilters.test.tsx`, which answers by method and full URL, and drive the fake WebSocket (`src/test/fakeWebSocket.ts`) as feature 20's tests do: open, `welcome`, `confirm_subscription`, then a `review_reminders` batch. Queries are scoped to their area (`within(main)`), because "Collections", "Collection", "Tags", "Due today", and "Overdue" each name more than one element.
  - **No earlier test changes.** The page alert shows only after a render failure, and the class changes change no text, role, or name, so no earlier assertion meets them. Item 2 of the checklist records the earlier test files, and item 21 checks them.
