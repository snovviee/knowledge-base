## Approach

- Data, API, WebSocket, UI: no change.
- Code: a generator in `backend/lib/test_mapping.rb` (Build may split it into files under `backend/lib/test_mapping/`), autoloaded through `config.autoload_lib`, and two Rake tasks in `backend/lib/tasks/test_mapping.rake`:
  - `docker compose run --rm backend bin/rails test_mapping:write` writes `specs/docs/test_mapping.md` and prints `Wrote specs/docs/test_mapping.md: <n> backend tests, <m> frontend tests.`, with exit status 0.
  - `docker compose run --rm backend bin/rails test_mapping:check` changes no file. When everything holds, it prints `Test mapping check passed: specs/docs/test_mapping.md is current.` with exit status 0. Otherwise it prints `Test mapping check failed:` on standard error, then one line per problem, and ends with exit status 1. The problems: `- specs/docs/test_mapping.md is out of date in: <parts>. Run bin/rails test_mapping:write.`, where the parts are "the summary" (everything before the first `## `), each `AC-NN` whose section differs, and "Tests with no known AC"; `- specs/docs/test_mapping.md does not exist. Run bin/rails test_mapping:write.`; `- A test has no known AC: <file>: "<name>".` for each such test (question 4); `- README.md "Test coverage" names a test that does not exist: <file>: "<name>".` for each (question 10). An AC that is "Not covered" is not a problem (question 11).
  - Both read files only, and never run a test (question 1). The backend container mounts the whole repository at `/app`, so the root is `Rails.root.parent` (`TestMapping.root`).
- What is read:
  - The ACs: the lines `- AC-NN: <text>` of requirements.md section 10. These are the known AC IDs (question 4).
  - Backend tests: `backend/spec/**/*_spec.rb` (RSpec's default pattern; `backend/.rspec` sets no other).
  - Frontend tests: `frontend/**/*.{test,spec}.{js,jsx,ts,tsx,mjs,cjs,mts,cts}`, without `frontend/node_modules/` (Vitest's default include and exclude; `frontend/vite.config.ts` sets neither).
  - Plans: `specs/features/NN_*/plan.md` belongs to AC-NN. Its `## Test plan` items are the lines `N. ` at the start of a line, each with the `Result:` lines below it up to the next item. Its `## Docs` checks are the lines `- [ ] ` and `- [x] ` at the start of a line.
  - The README: the table under the heading `Test coverage`, of level 2 or 3, up to the next heading of the same or a higher level. No such heading: nothing to check.
- What a test is:
  - A line that starts, after its indentation, with a test keyword followed by `(` or a space. RSpec: `it`, `specify`, `example`, `scenario`, their focused forms `fit`, `fspecify`, `fexample`, `fscenario`, their skipped forms `xit`, `xspecify`, `xexample`, `xscenario`, and `skip` or `pending` when the line opens a block (`do` or `{`). Vitest: `it` and `test`, alone or with `.only`, `.skip`, `.todo`, `.concurrent`, `.sequential`, `.fails`, or `.each(…)`.
  - Not tests (edge case): groups (`describe`, `context`, `RSpec.describe`, `xdescribe`, `xcontext`, `describe.skip`, and the like), even when their names hold an AC ID; calls such as `example.run`; `skip` or `pending` without a block, which are statements inside a test.
  - Its name is the first argument when that is one string literal with no interpolation: in Ruby `"…"` without `#{` or `'…'`; in JavaScript `'…'`, `"…"`, or `` `…` `` without `${`. It may begin on the line after `it(`. An escaped quote or backslash is read as the character. Anything else, such as a variable, a concatenation, an interpolated string, or `.each(…)`, is a name that is not plain text (question 4; edge case).
  - Its AC IDs are the run of `AC-NN` tokens at the start of the name, each followed by a space ("AC-13 AC-14 marks a note as reviewed…"). A test is listed under each of its IDs (question 5). A test with no ID, with an ID that requirements.md section 10 does not have, or whose name is not plain text is listed only under "Tests with no known AC" (question 4).
  - Skipped (question 6): the RSpec `x` forms and the `skip` and `pending` blocks; a test with `skip:`, `:skip`, `pending:`, or `:pending` in its metadata after the name; the Vitest `.skip` and `.todo` forms, and the options `{ skip: true }` or `{ todo: true }`; and every test inside a skipped group (`xdescribe`, `xcontext`, `describe.skip`, `describe.todo`, or a group with skip metadata). A group's extent is the lines indented deeper than its opening line, up to the next line at its indentation or less; RuboCop and the existing files keep the indentation. A skipped test is listed with " (skipped)" after its name and counted nowhere.
- Counts: an AC's backend and frontend counts are its tests that are not skipped, each counted once in each AC it is listed under. The totals count every test that is not skipped once, a test under two ACs included (question 5).
- Manual validation (question 2): "Test plan: <n> items, <m> passed", where an item passed when its last `Result:` line starts with "Pass" (an item that failed and then passed counts as passed; edge case), shown when the plan's Test plan has at least one item, linking to `../features/<folder>/plan.md#test-plan`. For AC-07, AC-26, AC-28, AC-29, and AC-30, the ACs whose result is a document (`specs/README.md`), also "Docs checks: <n>, <m> ticked", where ticked is `[x]`, linking to `…/plan.md#docs`. "1 item" is written in the singular. An AC with neither, and with tests, shows "None". An AC with no counted test and no manual validation is "Not covered" (question 11).
- Layout of `specs/docs/test_mapping.md` (question 8), in this order:
  1. The first line: ``Generated by `bin/rails test_mapping:write` from the test names and the plans. Do not edit this file by hand: run `docker compose run --rm backend bin/rails test_mapping:write` to write it again, and `docker compose run --rm backend bin/rails test_mapping:check` to check it.``
  2. The summary table `| AC | Acceptance criterion | Backend tests | Frontend tests | Manual validation |`, one row per AC in the order of requirements.md section 10: `[AC-NN](#ac-nn)`, its text, its two counts, and its manual validation (the parts joined by "; "), "None", or "Not covered".
  3. The totals line: `Totals: <n> backend tests and <m> frontend tests; a test listed under two ACs counts once. Of the 30 ACs, <a> have automated tests, <b> rely on manual validation alone, and <c> are not covered.` ("30" is the number of ACs in requirements.md.)
  4. The line `The nine cases that requirements.md section 7 requires are mapped by hand in the README's [Test coverage](../../README.md#test-coverage).` (question 3).
  5. One section per AC: `## AC-NN`, its text, then `Backend tests: <n>. Frontend tests: <m>. Manual validation: <…>.` or `Not covered.`, then one item per test file, `- [<file>](../../<file>)`, with one sub-item per test in the file's order: `  - <name>`, followed by ` (skipped)` when skipped.
  6. `## Tests with no known AC`: `- [<file>](../../<file>): <name>`, or for a name that is not plain text, ``- [<file>](../../<file>): `<the test's first line, trimmed>` ``; or `None.`
  - The order is fixed: ACs as in requirements.md, backend files before frontend files, files by path, tests in file order. The same files give the same text, so `check` can compare the whole file.
- The README's "Test coverage" table (question 3), written by Polish and read by `check` (question 10):
  `| Case (requirements.md 7) | AC | Tests |`, one row per case, with the tests in the third column as `` `<file>`: "<full name>" ``, separated by `<br>`, the file given from the repository root. A `"` or a `|` inside a name is written `\"` or `\|`. A test matches when its file has a test, skipped or not, with exactly that name.
- Decisions:
  - **Read the source, do not run the tests.** The backend container has no Node, and question 1 says neither command runs a test, so names must be plain text in the source (edge case: this binds the tests of every feature).
  - **Rake tasks, not a script in `bin/`.** They run in the backend container with the app's autoloading, as `sample_data:load` does (feature 26).
  - **The specs never read the real repository.** Each test builds a small repository in `Dir.mktmpdir` (requirements.md, test files, plans, a README) and stubs `TestMapping.root` to it. No test depends on the real tests or on the real mapping being current, so `bin/test` (AC-27) never fails because a test was added (question 1).
  - **No fixture line may look like a test.** The specs build fixture files with helper methods (for example `rspec_test("AC-06 …")`), never with heredocs or string lines that start with `it "`, `it('`, or `test(`. The generator reads `spec/lib/test_mapping_spec.rb` like any other test file, and a fixture such as an "AC-99" test there would appear in the real mapping and make the real check fail.
  - **The task spec** runs a task with `invoke` after `reenable`, and reads the exit status from the `SystemExit` that `abort` raises. The Rake tasks are loaded once per RSpec process, not once per file: a second `Rails.application.load_tasks` gives every task its actions twice, so a task would run twice, and RSpec runs the files in random order (`config.order = :random`). Feature 26's task spec also loads them (its plan). If that spec loads them without a guard, this feature's Build moves the loading into one helper in `spec/support/` that both specs call, for example `Rails.application.load_tasks if Rake::Task.tasks.empty?`, and records it under `## Deviations`.
  - **Build and Verify write no mapping in the main tree.** They write it in a scratch copy, or render it to standard output. Only Polish writes `specs/docs/test_mapping.md`, because only Polish writes `specs/docs/`.
  - **The mapping is the last Docs item.** Polish records the Test plan results, ticks the other Docs items and then the mapping item, and only then runs `write` and `check`, so the mapping counts this plan's own results and ticks. From this feature on, every Polish ends the same way (question 9).
  - **The check stays out of `bin/test`** (question 1, edge case). Nothing in this plan changes `bin/test`.
