## Approach

- Data: no change. Feature 12 adds `notes.last_reviewed_date` (date, null), always null until this feature sets it. No migration here.
- "Today": `User#today` (feature 12): the current date in the user's saved zone, or in UTC without one (feature 12 question 1).
- API (JSON under `/api`, as in [docs/api_contract.md](../../docs/api_contract.md)):
  - `POST /api/notes/:id/review` (spec question 5): a member route of `resources :notes`, action `Api::NotesController#review`.
  - Request: no body, and the header `X-CSRF-Token`. A body that is JSON is ignored, whatever it holds (spec question 4).
  - Response `200`: `{ "note": <detail> }`, the same detail as `GET /api/notes/:id`, with `"last_reviewed_date"` the user's today (`"YYYY-MM-DD"`).
  - Any note of the user: active or archived, with any interval, None included (spec question 1), and on any day, before its next review date included (spec question 3).
  - Only `last_reviewed_date` changes. Every other field stays, the updated date included (spec edge case: "the other fields stay"; requirements.md 3.4 lists the updated date among a note's fields). The next review date stays too (spec question 8); feature 14 changes that.
  - A second review on the same day writes nothing: the answer is the same as the first (spec question 2).
  - Errors, in this order: 401 `unauthenticated`; 400 `bad_request` for a body that is not JSON (spec question 9); 403 `invalid_csrf_token`; 404 `not_found` for another user's note, a deleted one, or an id that is not a number. A refused request changes nothing (spec question 5; edge cases). This is the order of every request that changes data (docs/api_contract.md, Order of checks).
- WebSocket: none.
- UI (`frontend/src/NoteDetail.tsx`):
  - A row "Last reviewed" right after feature 12's "Next review" row, in the same `dt`/`dd` form: the date as feature 12's `formatReviewDate` writes it ("Nov 9, 2026"), or "Never" when `last_reviewed_date` is null. A note whose answer has no `last_reviewed_date` (the older test fixtures) reads as "Never" (spec question 7).
  - A "Mark as reviewed" button, first in the detail's actions (before "Edit"), for every note (spec questions 1, 6). It hides with the other actions while the delete confirmation is open (feature 09 question 12).
  - Choosing it sends `sendWithCsrfToken('POST', '/api/notes/<id>/review')`, with no body. While the request waits, the button is disabled with `aria-busy="true"` ([conventions: Busy button](../../docs/conventions.md#ui)).
  - 200: the detail shows the answer's note, and "Marked as reviewed." shows with `role="status"`, above the actions, where the archive's failure shows.
  - 401: `onSignedOut`, so the app shows the sign-in screen. 404: the detail's `gone` state, so `Notes` takes the note off the list and shows "This note no longer exists.", as archive does. No answer, or any other answer: the alert "Could not mark the note as reviewed. Try again." in the same place, and the detail keeps its note (spec question 6).
  - Starting a review removes the previous review's status or alert, as an archive removes its previous failure. Both go with the detail when it closes.
  - The detail does not pass the review's answer to the list (see Decisions).
- Decisions:
  - The review is a member action of `Api::NotesController`: it reuses the lookup through `current_user.notes`, the 401 check that runs first (`prepend_before_action :require_signed_in_user`), and `note_json`. One place builds a note's JSON, so the fields later features add to a note (feature 15's `review_state`) reach the review's answer too.
  - `Note#mark_reviewed!` sets `last_reviewed_date` to `user.today` and saves with `save!(touch: false)`. `touch: false` keeps `updated_at` (spec edge case: only the last reviewed date changes). A save, not `update_columns`, so validations and model callbacks run as for any other save of a note, and later features can rely on them. Dirty tracking writes nothing when the date is already today (spec question 2). Probe of 2026-11-09 (lane p13): `save!(touch: false)` keeps `updated_at`, and `update!` changes it.
  - The action reads no field of the body, only `params[:id]` (spec question 4). A body that is not JSON still answers 400, because the anti-forgery check reads the parameters before the action runs. The same probe saw, for an action that reads no body field: no sign-in 401, then a body that is not JSON 400 (with or without a token), then no token 403.
  - Feature 14 changes the next review date at a review, so no AC-13 test asserts a next review date that feature 14 changes. Every scheduled note in an AC-13 test or Test plan item has a next review date equal to today plus its interval at the time of the review (for example, weekly with 2026-11-16 on 2026-11-09), so feature 14's recalculation gives the same date. A note with the interval None has no date before or after. So feature 14 replaces no AC-13 test.
  - The list is not updated by a review in this feature. A list entry shows the next review date (feature 12), not the last reviewed date, so nothing it shows changes here, and no test could require the update (strict TDD). Feature 14 passes the answer to the list, with its list test. So the review has its own handler in `NoteDetail.tsx` and does not reuse archive's `changeStatus`, which calls `onChanged`.
  - Time in backend tests: `before { travel_to Time.utc(2026, 11, 9, 20, 0) }` and `after { travel_back }`, with `include ActiveSupport::Testing::TimeHelpers`, as feature 12's specs do. At that hour the date is 2026-11-10 in Asia/Tokyo. A later `travel_to` or `travel` in a test is called without a block, since a block call nested in a `travel_to` raises.
  - The frontend computes no date: it shows the answer's dates with `formatReviewDate`, which is pinned to UTC (feature 12). Its tests need no fake clock.
  - New test files, so the earlier ones keep their assertions: `spec/requests/mark_reviewed_spec.rb` and `src/MarkReviewed.test.tsx`. The frontend file copies the fetch stub of `src/Notes.test.tsx`, which answers by method and path, and its fixtures carry feature 12's review fields. Its queries are scoped to the notes area.
  - Unscoped queries in earlier tests (spec, Notes for Plan): the new status and alert show only after a review, so the AC-09 tests' `getByRole('status')` and `findByRole('alert')` never meet them. If an AC-12 test lists the detail's rows or actions exactly, it encodes the state before this feature (requirements.md 4 asks for the last reviewed date and the action): replace that assertion with item 12's or item 13's test, and record it under Deviations, as feature 11 did with feature 09's interim assertions.
  - The test that requirements.md 7 asks for (mark a note as reviewed, and the next review date is recalculated) needs feature 14's recalculation, so it is feature 14's item 2, named with both AC IDs.
  - Pipelined run: feature 12 is at Build on 2026-11-09. If it is not Done when this Build starts, Build records that under Deviations (owner's standing instruction).
