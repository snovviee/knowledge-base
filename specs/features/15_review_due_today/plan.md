# Plan: 15_review_due_today

## Approach

- Data: no change. A note's review state comes from feature 12's `status`, `review_interval`, and `next_review_date`, and the user's today (`User#today`, feature 12: the date in the user's saved zone, UTC without one).
- Review state: one place in `Note` that features 16 and 18 to 20 call (spec questions 1, 2):
  - `Note#review_state(today)` → `"due_today"` for an active note whose interval is not `none` and whose next review date equals `today`; `"overdue"` for such a note whose date is before `today` (requirements.md 3.5; feature 16 shows it); `nil` for any other note: archived, interval `none`, or a later date.
  - `Note.due_today(today)` → a relation of exactly the notes whose `review_state(today)` is `"due_today"`. It is built from two scopes: `Note.active` (status `active`) and `Note.scheduled` (interval not `none`). It chains on a user's notes: `user.notes.due_today(user.today)`.
  - Feature 16 adds `Note.overdue(today)` in the same way. The two relations never share a note. Feature 20 can build a batch from `user.notes.due_today(today).or(user.notes.overdue(today))`, and take each reminder's state from `note.review_state(today)`.
  - `today` is always passed in, never read inside, so one request or one batch uses one date for every note: `today = user.today`, read once.
- API (JSON under `/api`, as in [docs/api_contract.md](../../docs/api_contract.md)):
  - Every note in an answer gains `"review_state"`: `"due_today"`, `"overdue"`, or `null` (spec question 2). That is `GET /api/notes`, `GET /api/notes/:id`, the 201 of `POST /api/notes`, the 200 of `PATCH /api/notes/:id`, and the 200 of `POST /api/notes/:id/review` (feature 13). It uses the user's today, read once per request.
  - `GET /api/notes?review=due_today`: 200 `{ "notes": [ <summary>, ... ] }` with only the notes due today, newest first (spec questions 4, 10; feature 09 question 2).
  - `review` left out, or `""`: no filter. The answer has all the user's notes, as before (spec question 10).
  - Any other `review`, another letter case or a list included (`soon`, `Due_Today`, `review[]=due_today`): 422 `{ "error": "validation_failed", "fields": { "review": "invalid" } }` (spec questions 4, 10). Feature 16 adds the value `overdue`, and feature 17 adds `next_7_days` and `unscheduled`.
  - No sign-in: 401 `{ "error": "unauthenticated" }` before anything else, whatever `review` is (spec edge case).
- WebSocket: none.
- UI:
  - `frontend/src/Notes.tsx`: `NoteSummary` gains `review_state?: 'due_today' | 'overdue' | null`. A note whose answer has none (the older test fixtures) reads as null. A list entry whose `review_state` is `"due_today"` shows "Due today" right after feature 12's `note-review` element ("Next review: Nov 9, 2026"), in an element with `data-testid="note-review-state"`. It is not a list item, so the AC-09 `listitem` queries keep their meaning (spec questions 2, 3).
  - `frontend/src/NoteDetail.tsx`: the "Next review" row (feature 12) shows the date, then "Due today" in an element with `data-testid="note-review-state"`, for a note whose `review_state` is `"due_today"` (spec question 3). The detail shows the state of the note it holds: as read when it opened, or as the answer to a create, a save, an archive, a restore, or a review gave it (spec edge case "A detail shows the state as of its opening, and then as of the answer to a change made in it").
  - The "Review" filter, in a new `frontend/src/NoteFilters.tsx`: a select labelled "Review" by a `<label>`, with the choices "All" (value `""`, chosen at first) and "Due today" (`due_today`), above the list (spec questions 4, 8). `Notes` keeps its value, and shows it only with the list (`view.kind === 'list'`), in every state of the list: loading, failed, empty, or with notes. A detail or a form hides it and keeps its value. The address of the page does not change, so a reload starts at "All" (spec question 8).
  - The list request: `fetch('/api/notes')` with "All", and `fetch('/api/notes?review=due_today')` with "Due today", each with the address alone, as now. One function, `notesAddress(filters)` in a new `frontend/src/notesAddress.ts`, builds the address from the filter values and leaves out a filter that is at "All"; features 16 and 17 extend it. It is a module of its own, as `tagChanges.ts` is, because the lint rule `react-refresh/only-export-components` flags a component file that also exports a function.
  - Choosing a choice loads the list: "Loading…" with `role="status"` in place of the entries, while "Review" shows the choice and can be changed again. Only the answer to the latest choice shows (spec question 7). A 401 shows the sign-in screen. No answer, or any other error answer, shows "Could not load notes. Try again." with `role="alert"` and "Try again", which asks again for the same address (spec question 7; [conventions: Load error with Try again](../../docs/conventions.md#ui)).
  - Empty: with "Due today", an empty list shows "No notes are due for review today." in place of the entries; with "All", "No notes yet" as before (spec question 5).
  - States hold as of the list load. The list never asks again on its own, and the browser never computes a state: the labels come from `review_state` alone. A note changed in this tab (edited, reviewed, archived, or restored) replaces its entry with the answer's note and label and keeps its place, and a created note goes to the top, until the list loads again (spec questions 6, 9; feature 14 passes the review's answer to the list).
- Decisions:
  - The state rule lives in `Note`, in Ruby (`review_state`) and in SQL (`due_today`), and one model test checks that the two agree on the same notes. A later feature calls them and never restates the rule.
  - The filter is a small model, `NoteListFilter` (`backend/app/models/note_list_filter.rb`, `ActiveModel::Validations`). It takes the request's parameters and `today`, adds `invalid` on `review` for a value it does not know, and applies the chosen scope to `current_user.notes`. A refusal goes through `render_validation_failed`, so the 422 body is the one of features 06 and 09, and feature 17's parameters (`search`, `status`) can be named in the same answer by adding validations.
  - `Api::NotesController#today` keeps `current_user.today` for the request. `summary_json` adds `review_state: note.review_state(today)`, so every answer carries it, the review's included (feature 13's `note_json` builds on `summary_json`).
  - Frontend loading. `Notes` builds the list address from the filter, and an effect keyed on that address and a retry count loads the list. Each answer is kept with the key it answers. While the kept answer is for another key, the list shows "Loading…". The effect's cleanup drops an answer that arrives after the key changed, so only the latest choice shows. Choosing a choice and "Try again" only change the key, so no state is set synchronously inside an effect: the rules `react-hooks/set-state-in-effect` and `react-hooks/refs` are on (eslint-plugin-react-hooks 7.1.1, probed on 2026-11-09). A create, a save, an archive, a restore, or a review changes the kept answer, as `withNote` and the create do now.
  - `fetch` keeps a single argument, the address. So the earlier tests' stubs, keyed by method and URL, and the AC-09 count of `url === '/api/notes'` keep working.
  - Features 16 and 17 add choices after "Due today", and feature 17 adds query parameters. So no AC-15 test pins the whole list of choices or of `review` values: a test checks that the choices start with "All" and "Due today", and an unknown value is one that no feature adds (`soon`). An exact address is asserted only where "Review" is the only filter set; feature 17 leaves out filters at "All", so `/api/notes?review=due_today` stays the address there.
  - Exact-shape assertions of earlier request specs: feature 09's `full_json` and the list's first entry in `spec/requests/notes_spec.rb`, and `full_json` in `spec/requests/note_move_spec.rb`, compare whole notes with `eq`. They gain `"review_state" => nil` (item 5), as feature 12's item 10 added the review fields; no `expect` line changes. Feature 12's `review_interval_spec.rb` uses `include`, and features 13 and 14 compare an answer with another answer, so they need no change.
  - Unscoped queries in earlier tests (spec, Notes for Plan). The filter has no status, no alert, no list, and no list item, and it shows only with the list, where no earlier test looks for "Due today". The choice "Due today" has the label's text, so the AC-15 tests find the label in its entry or in the detail's "Next review" row.
  - With the label in the "Next review" row, that row's whole text is "Nov 9, 2026" followed by "Due today". Feature 12's `detailRow` reads it whole, but no AC-12 to AC-14 fixture has a `review_state`, so those tests see the date alone.
  - Time in tests. Backend tests fix the time with `travel_to Time.utc(2026, 11, 9, 20, 0)` (`ActiveSupport::Testing::TimeHelpers`), as features 12 to 14 do: at that hour the date is 2026-11-10 in Asia/Tokyo. The frontend computes no date. Item 10's test fakes only `Date` (`vi.useFakeTimers({ toFake: ['Date'] })` and `vi.setSystemTime`) to show that a label comes from `review_state` and not from the clock.
  - New test files, so the earlier ones keep their assertions: `spec/models/note_review_state_spec.rb`, `spec/requests/review_due_today_spec.rb`, and `src/ReviewDueToday.test.tsx`. The frontend file copies the fetch stub and the fixtures of `src/ReviewInterval.test.tsx` (feature 12), whose stub answers by method and full URL, query included, and adds `review_state` to its fixtures. A helper lists the list requests: the URLs whose path is `/api/notes`, in order.
  - Pipelined run: features 12 to 14 come right before this one. If one is not Done when this Build starts, Build records that under Deviations (owner's standing instruction).

## Test plan

Walkthrough for Verify, against the running app. With the Verify harness (`verify/README.md` in the run's scratchpad): `up.sh <slot>`, `mint.sh` for each user, Playwright through `pw.sh` (`kb.openApp`, `kb.api`, `kb.block`), `curl.sh`, and `rails.sh`. By hand: `docker compose up`, then http://localhost:3000.

- **Users.** A is "Ada Lovelace" (`mint.sh <slot> google a-1 "Ada Lovelace"`), B is "Grace Hopper" (`mint.sh <slot> github b-1 "Grace Hopper"`), and C is "Charles Babbage" (`mint.sh <slot> google c-1 "Charles Babbage"`). Item 17 mints a second sign-in of A (`a-1` again).
- **Zone and dates.** Every page opens with `timezoneId: 'Europe/Berlin'` unless the item names another zone, so A's saved zone is Europe/Berlin. T is A's today on the server, printed after A's first page load by `rails.sh <slot> 'puts User.find_by!(display_name: "Ada Lovelace").today'`. T+n and T−n are n days later or earlier. The UI writes a date like "Nov 9, 2026", the API like "2026-11-09". Values in square brackets are for T = 2026-11-09. Run the walkthrough within one day in Berlin.
- **Data.** Before item 1, A's page makes, in this order (`kb.api(page, 'POST', ...)`, so each later note is newer), the collection "Work" and these notes in it, each with the body "B": "Rails tips" (`"review_interval": "weekly"`, `"next_review_date"` T), "Tomorrow tip" (weekly, T+1), "Late tip" (weekly, T−1), "Archived tip" (weekly, T; then `PATCH` `{"status": "archived"}`), "Someday" (no `review_interval`), and "Ruby tips" (weekly, T).
