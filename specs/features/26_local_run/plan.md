## Approach

- Data: no new table or column. The sample data reads `sign_ins` and `users`, and writes `collections`, `tags`, `notes`, and `note_tags` through their models. It sets every stored note field the specs define through feature 25: `title`, `body`, `source_url`, `status`, the collection, the tags, and feature 12's `review_interval`, `review_interval_days`, `next_review_date`, and `last_reviewed_date`. Feature 17's search copies (`search_title`, `search_body`, `search_source_url`) are filled by its model callback when a note is saved, so the sample data sets nothing for them. The user's saved time zone (feature 12) is read through `User#today` and never written. Reminder dismissals (feature 23) are not sample data: question 10 names none, and a new workspace has none.
- API, WebSocket, UI: no change. The app shows the sample data with its existing screens.
- Server start (spec question 2):
  - `backend/bin/dev` (today `exec "./bin/rails", "server", *ARGV`) first runs `bin/rails db:prepare` with `SKIP_TEST_DATABASE=1`. Only when that succeeds does it replace itself with `bin/rails server` and the arguments it was given. A failed prepare ends `bin/dev` with a failure status, and no server starts.
  - `compose.yaml` gives the backend service `command: ["bin/dev", "--binding=0.0.0.0", "--port=3000", "--pid=/tmp/rails-server.pid"]`, and the backend stage of the `Dockerfile` gets the same `CMD`. `docker/backend-entrypoint.sh` stays as it is: it installs gems, then runs the command it is given.
- Sample data (spec questions 5 to 12):
  - The command `bin/rails sample_data:load` is a rake task, `backend/lib/tasks/sample_data.rake`, over the class `SampleData` in `backend/lib/sample_data.rb` (autoloaded through `config.autoload_lib`).
  - `SampleData.load!` checks, in this order, and at the first refusal raises `SampleData::Refused` with its message and adds nothing:
    1. the environment is development or test (`Rails.env.local?`); else "Sample data is for the development and test environments only." (question 11);
    2. a sign-in exists; else "No one is signed in. Sign in with Google or GitHub, then run this again." (question 7);
    3. the user of the newest sign-in has no collection, no tag, and no note; else "<display name> (<Google or GitHub>) already has collections, tags, or notes, so no sample data was added. To start over, see "Sample data" in the README." (questions 8, 9).
  - Then it adds the data below in one transaction, and returns the user and the numbers of collections, tags, and notes it created.
  - The task prints "Added sample data for <display name> (<Google or GitHub>): 3 collections, 4 tags, 10 notes." to standard output and ends with status 0 (question 12). A refusal prints its message to standard error and ends with status 1 (question 9). Any other error ends the task with Rails' own error output, and the transaction leaves nothing behind (question 10).
  - The provider's name in the messages: `google_oauth2` is "Google", and `github` is "GitHub".
- The sample data (spec question 10). T is the user's today when the command runs: `User#today` (feature 12), the date in the user's saved time zone, UTC without one. Dates are stored as calendar dates, so the states move on with the days (spec edge case).

  - Tags: "habits", "rails", "someday", which is on no note, and "testing".

- Decisions:
  - **`bin/dev` prepares the database, not the entrypoint.** Compose's `command` runs `bin/dev` from the mounted checkout. An image keeps the entrypoint and the `CMD` it was built with, and `docker compose up` does not rebuild an existing image, so a change there would need a one-time `docker compose build` on every checkout that already has images, the owner's among them. The spec's draft note proposed the entrypoint; this gives the same behavior without that step. `docker compose run --rm backend <command>` replaces the command, so the tests, the console, the linters, and `db:reset` never prepare the development database (question 2). The `Dockerfile`'s `CMD` is changed to match, so the image and Compose start the server the same way.
  - **`SKIP_TEST_DATABASE=1` on the prepare.** In development, `db:prepare` also prepares the test database unless `SKIP_TEST_DATABASE` or `DATABASE_URL` is set (activerecord 8.1.4.1, `DatabaseTasks#each_current_environment`, read on 2026-11-09). A server start must not touch the database that a test run may be using (features/27_local_tests question 3). The Verify harness's `up.sh` sets the same variable for the same reason.
  - **A rake task, not `db/seeds.rb`.** `db:prepare` runs the seeds when it creates a database, before anyone has signed in (question 6). `db/seeds.rb` stays as it is, comments only, so a new database starts empty.
  - **Through the models, in one transaction.** `create!` runs every validation and callback: the name tidying and `folded_name` of collections and tags, feature 12's schedule rules, and feature 17's search copies. So a feature that fills a column in a model callback needs no change here. The transaction makes the load all or nothing (question 10). The data is held in constants of `SampleData`, with each date as a number of days from T, and the dates are `Date` values computed from `user.today`; feature 12's validation accepts a `Date` as is. Notes are created from 10 down to 1, so the newest-first list (created date, then id) shows them in the table's order.
  - **The newest sign-in is the newest row of `sign_ins`:** `SignIn.order(created_at: :desc, id: :desc).first`. Logout deletes the row (feature 05), so only sign-ins that logout has not ended are left. A cookie that expired leaves its row ([domain/users.md](../../docs/domain/users.md#rules)), so that sign-in still counts (question 7, edge case).
  - **"Has data"** is `user.collections.exists? || user.tags.exists? || user.notes.exists?`. The saved time zone and the sign-ins are not looked at (question 9, edge case).
  - **A page that is open during the load.** The task runs in its own process, and Action Cable's development adapter (`async`, `config/cable.yml`) reaches only the server's own process. So an open page shows the data after a reload, and its reminders panel (feature 20) with its next 60-second check. Polish documents this from the app as built; the README tells the developer to reload.
  - **Tests.** A script test runs the script in the backend container, where the repository is at `/app`, with fakes in a temporary folder. `backend/spec/support/script_helpers.rb` (new; feature 27 reuses it) writes a fake executable and runs a command through `Open3`, returning its output, its errors, and its status. The task's tests invoke the rake task in the test process through `backend/spec/support/rake_helpers.rb` (new; feature 29's task spec reuses it): it loads the app's tasks once (`Rails.application.load_tasks` unless `Rake::Task.task_defined?("sample_data:load")`), runs a task with `invoke` after `reenable`, and gives back its standard output, its standard error, and its exit status (0 without `SystemExit`, else the `SystemExit` status). The review states are read through the app's own API (`review_state` of features 15 and 16; `review=next_7_days` and `review=unscheduled` of feature 17), so they follow the app's definitions (item 14). The stored dates they come from are checked on their own, against `User#today` (item 10). Every test that depends on the date fixes the time with `travel_to`, at 2026-11-09 20:00 UTC for a user in "Asia/Tokyo" (2026-11-10 there), as feature 12 does (features/27_local_tests question 5).
  - **Scenarios and edge cases with no checklist item.** "Before the first frontend build" (question 3 chose no placeholder: these are Rails' own pages, the welcome page for `/` and the 404 pages for other addresses; changed 2026-11-10, see Deviations), "The port is already taken" (Compose's fixed port mapping, unchanged), and "Start over" (Rails' `db:reset`; the empty seeds are item 4) need no code, and the Test plan walks them (items 3, 4, 11). So do the edge cases that describe Docker, Compose, and Rails as they are: the Compose version, the files owned by root on Linux, the network at the first start, the app open to this machine only, migrations that arrive while the app runs (Test plan item 2), and `db:reset` deleting every user's data (item 11); the README states each (Docs item 1). The three README scenarios are accepted by `## Docs` (specs/README.md: the result of AC-26 is a document).
