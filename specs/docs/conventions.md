# Conventions

## UI

- **Loading.** While the app checks the session, the page shows a status line "Loading…" with `role="status"`. The app does not flash the sign-in screen first (AC-01, AC-04).
- **Sign-in error.** A failed or cancelled sign-in comes back as `?sign_in_error=google` or `?sign_in_error=github`. The sign-in screen names that provider: "Sign-in with Google did not complete. Try again." or "Sign-in with GitHub did not complete. Try again." It is shown with `role="alert"`, and the parameter is removed from the address (AC-01, AC-02).
- **Busy button.** After either sign-in button is chosen, both sign-in buttons are disabled and have `aria-busy="true"`, so a second click starts no second sign-in (AC-01, AC-02).
- **Empty states.** The main layout shows "No collections yet" in the collections area (AC-01, AC-06), "No tags yet" in the tags area (AC-08), and "No notes yet" in the notes area (AC-01). Later features keep the same wording rule. The notes area also has the messages of the filter bar (see "A filtered list").
- **Loading inside an area.** An area that loads a list shows "Loading…" with `role="status"` in its own place, while the rest of the layout shows (AC-06).
- **Load error with Try again.** A list that cannot load shows "Could not load collections. Try again." (or the area's own message) with `role="alert"` and a "Try again" button. The button shows "Loading…" and loads the list again (AC-06, AC-04).
- **Forms in place.** A create or rename form opens in its place in the list, with the focus in its name field. "Cancel", Escape, or opening another form closes it with no request. One form or confirmation is open at a time. The create, save, and delete buttons are busy while their request waits, the same way as the sign-in buttons (AC-06).
- **Validation messages.** A refused name shows its message under the field, with `role="alert"`. The field gets `aria-invalid="true"` and `aria-describedby`. The messages are "Enter a name." (`blank`), "Use at most 100 characters." (`too_long`), and "A collection with this name already exists." (`taken`). The first two are in `frontend/src/NameListArea.tsx`, and the third is in `frontend/src/Collections.tsx` (AC-06).
- **Change failures.** A create, rename, or delete with no answer, or with an error answer, shows "Could not create the collection. Try again.", "Could not rename the collection. Try again.", or "Could not delete the collection. Try again." as an alert. The form or the confirmation stays open with the typed name (AC-06).
- **A refused delete.** A collection that still has notes is not deleted. Its delete confirmation stays open and shows "This collection still has notes. Move or delete them first." as an alert, in place of the general failure above. "Delete" can be chosen again once the notes are gone. Tags have no refusal, so their confirmation shows only the general failure (AC-07).
- **Delete confirmation.** The row asks "Delete “<name>”? This cannot be undone." with "Delete" and "Cancel". The focus is on "Cancel", and only "Delete" sends the request (AC-06).
- **A record that is gone.** A rename or delete answered 404 takes the row off the list. A rename also shows "This collection no longer exists." as an alert (AC-06).
- **Sign-in ended.** A list or change request answered 401 shows the sign-in screen with no message (AC-05, AC-06). So does a WebSocket `disconnect` message with `"reconnect": false`: the refusal of the connection, a logout's close, and the close of a connection whose sign-in is gone. The app then opens no connection until the next sign-in. So a logout in one tab shows the sign-in screen at once, with no reload, in each other tab of the browser whose connection is open. A tab whose connection is not open at that moment (still opening, or lost) keeps the main layout until it next asks the server. This narrows feature 05's edge case "Logged out in another tab" (AC-22).
- **The real-time connection.** The main layout opens one WebSocket when it shows, keeps that one while the page re-renders, and closes it when the sign-in screen takes its place: after a logout, a 401, or a refusal. The loading screen, the server-error screen, and the sign-in screen open none. A close without `"reconnect": false` is a loss, not a sign-out: the panel shows the offline alert and the client connects again on its own (see "The review reminders panel" below; AC-20, AC-22).
- **Logout.** The header shows the display name and a "Log out" button. The button is busy while its request waits. A failed logout shows "Could not log out. Try again." with `role="alert"` under the header, and the main layout stays (AC-05).
- **Server error on page load.** When the session check cannot reach the server, or gets an answer other than success or 401, the page shows "Could not reach the server. Try again." with `role="alert"` and a "Try again" button. The button checks the session again. The sign-in screen does not show (AC-04).
- **Screen failure.** A part of the page that fails to draw replaces the whole page with a full-page screen: "Something went wrong. Reload the page." with `role="alert"`, and a "Reload page" button, in the look of the server-error screen. `PageErrorBoundary` in `frontend/src/PageError.tsx` (a React error boundary) wraps the page: `App` in `frontend/src/App.tsx` renders `AppPage` inside it. "Reload page" calls `reloadPage()` from `frontend/src/reloadPage.ts` (`window.location.reload()`, a module of its own so a test can replace it), and the reloaded page checks the session as every page load does. A failed request never brings this screen: a boundary catches only errors thrown while drawing, and each request shows its own message in its own place. The reload loses what was typed in an open form (AC-24).
- **Hover and focus.** Every button, link, field, drop-down list, text area, and checkbox that is shown and enabled has a hover state, a `hover:` class that changes its background, border, text color, or underline, and keeps a visible focus: the browser's outline, or a ring (`focus:ring-2 focus:ring-slate-300`) where `focus:outline-none` takes the outline away. Fields use `hover:border-slate-400 hover:bg-slate-50` (the name forms, `fieldClass` in `frontend/src/NoteForm.tsx`, and `CONTROL` in `frontend/src/NoteFilters.tsx`); a filled button `hover:bg-slate-700` (a delete, `hover:bg-red-800`); an outlined, plain, or row-action button `hover:bg-slate-100` ("Dismiss" `hover:bg-red-50`); a note's title in the list `hover:underline`. A checkbox's hover is on its row: the `<label>` that holds it (`rounded hover:bg-slate-100`). The elements that only the app moves the focus to (`tabIndex={-1}`: a note's title in its detail, the "Tags" group, the heading "Review reminders") have no ring, and a disabled element needs no hover (AC-24).
- **Looks.** One look per kind of element, so the screens read alike. A feature that adds an element gives it the look of its kind (AC-24):
  - Font: the default sans family everywhere; no `font-mono` or `font-serif`.
  - Area heading (`h2` of "Collections", "Tags", "Review reminders", "Notes"): `font-semibold`, 16 px. View heading (`h3`: a note's title in its detail, "New note", "Edit note"): `text-lg font-semibold`.
  - Field label (each `<label>` tied to a control, and each `<legend>`: the name forms, the note forms, the filter bar): `text-xs font-medium text-slate-600`. Field message (under a field or a group): `text-xs text-red-700`.
  - Main-layout text (list entries, a detail's fields, empty states, "Loading…" lines, alerts): `text-sm`; empty states and "Loading…" in `text-slate-600`, alerts in `text-red-700`.
  - Buttons of the main layout, four kinds: filled (`rounded px-3 py-1 text-sm text-white` on `bg-slate-900`, or `bg-red-700` for the "Delete" that confirms a delete): "Create", "Save", "Try again"; outlined (`rounded border px-3 py-1 text-sm`): "Edit", "Archive", "Restore", "Delete" and "Mark as reviewed" in a detail, "Cancel", "Log out", "Clear search and filters"; plain (`rounded px-2 py-1 text-sm`): "New collection", "New tag", "New note", "Back to notes"; row action (`rounded px-1.5 py-1 text-xs`): "Rename" and "Delete" in the lists, "Open" and "Dismiss" in the panel. The notes' titles in the list read as entry text and are none of these.
  - Full-page screens (loading, server error, sign-in, screen failure): text at 16 px, buttons filled with `rounded px-4 py-2`.
  - Side padding: 16 px (`px-4` or `p-4`) on the header, each section of the left area, the reminders panel, and the notes area.
  - The status labels inside an entry or a detail ("Archived", "Due today", "Overdue") and "Marked as reviewed." keep their own look and belong to no kind.
- **Light theme only.** The app has one theme. No class uses the `dark:` variant, no style reads `prefers-color-scheme`, and nothing sets `color-scheme`, so a dark system theme changes nothing: the page and its controls draw in their light look. Each full-page screen and the main layout paint their own white (`bg-white`), and `body` has no background of its own (AC-24).
- **UI tests.** `frontend/src/test/ui.ts` holds the helpers that read the Tailwind classes, because jsdom applies no CSS: `interactiveElements(root)` (the shown, enabled buttons, links, fields, drop-down lists, and text areas), `hoverClasses(element)`, `keepsFocusVisible(element)`, and `lookOf(element)` (font, size, weight, color, padding, rounding, border, and background from the classes). The sweeps of `frontend/src/UiQuality.test.tsx` walk every screen with them: every interactive element has a hover state, Tab reaches each in turn with a visible focus, each element of a kind has the kind's look, and no style follows a dark theme. A feature that adds an element must keep them green. `frontend/src/UiStates.test.tsx` guards the empty, loading, busy, validation, and error states, and `frontend/src/PageError.test.tsx` the screen failure (AC-24).

- **The notes area.** It shows one view at a time, in place: the list, a note's detail, the new-note form, or the edit form. "Back to notes" returns to the list, and the address does not change (AC-09). "No notes yet" is its empty state, and "New note" opens the form.
- **Browser checks on submit.** "Create" and "Save" check the fields first. Each field that breaks a rule shows its message under it, is marked `aria-invalid`, and the first such field gets the focus. Nothing is sent. The messages are "Enter a title.", "Use at most 200 characters.", "Enter a body.", "Use at most 100,000 characters.", "Enter a URL that starts with http:// or https://.", "Use at most 2,000 characters.", and "Choose a collection." The server's 422 answer shows its codes the same way, and "This collection no longer exists. Choose another." for `collection_id` `not_found` (AC-09). The edit form shows the collection's messages too (AC-11).
- **Note failures.** A note create, save, archive, restore, or delete with no answer, or with an error answer, shows "Could not create the note. Try again.", "Could not save the note. Try again.", "Could not archive the note. Try again.", "Could not restore the note. Try again.", or "Could not delete the note. Try again." The form, the detail, or the confirmation stays open (AC-09).
- **Escape.** Escape does not close the note form, so a long body is not thrown away by a stray key. Escape does cancel a delete confirmation (AC-09).
- **Focus.** An opened detail puts the focus on the note's title. A delete confirmation puts it on "Cancel" (AC-09).
- **A note changed in its detail.** A note saved in its edit form, archived, restored, or marked as reviewed keeps its place in the list, and its entry shows the server's answer, with its new values, with no list request. `Notes` replaces the entry with `withNote`: a save through `noteSaved`, and an archive, a restore, or a review through the detail's `onChanged` callback, which gets only a 200 answer's note (AC-09, AC-14).
- **A renamed collection.** A collection renamed in the collections area shows its new name on its notes, in the list and in an open detail, with no notes request. `NameListArea` takes an `onRenamed` callback for areas that show a collection's name; `App` keeps each rename by id, and `Notes` shows it at render time (AC-09).
- **The Collection group in the note form.** The new-note and the edit form show the same "Collection" group: a fieldset whose legend "Collection" also labels its select, so the select is found by the label "Collection". The choices are "Choose a collection", then the user's collections in the server's order (AC-09, AC-11). In the edit form the note's collection is chosen, and the group loads the collections on its own while the rest of the form works, as the Tags group does: "Loading…" with `role="status"`, then the select, or "Could not load collections. Try again." with `role="alert"` and "Try again" (AC-11). The new-note form keeps its own loading, failure, and no-collections states above its fields, and shows the group once the collections are there (AC-09). The edit form sends `collection_id` only when another collection is chosen, so a save made while the group loads or has failed keeps the note in its collection. "Choose a collection." and "This collection no longer exists. Choose another." show under the select, which gets `aria-invalid` and the focus (AC-11).
- **The Tags group in the note form.** The new-note and the edit form show a "Tags" group, one checkbox per tag. The group loads the tags on its own, while the rest of the form works (AC-10). Its states are "Loading…" with `role="status"`, "Could not load tags. Try again." with "Try again" when the tags cannot load, and "No tags yet" when the user has none.
- **A chosen tag that no longer exists.** When a create or a save answers 422 with `tag_ids` `not_found`, the group shows "A chosen tag no longer exists. Check the tags again." with `role="alert"`, loads the tags again, keeps the checks of the tags that still exist, and moves the focus to the group. The form keeps what was typed (AC-10).
- **Tag names in the list and the detail.** A note's tags show after its collection's name in the list, as plain text in an element that is not a list item, and as "Tags" with the names, or "No tags", in the detail (AC-10).
- **A tag's delete confirmation.** The tags area's confirmation adds the line "Notes with this tag are kept." under "Delete “<name>”? This cannot be undone.". Collections have no such line (AC-10).
- **A renamed or deleted tag.** A tag renamed in the tags area shows its new name on its notes, and a deleted tag leaves them, in the list and in an open detail, with no notes request. `NameListArea` takes an `onDeleted` callback as well as `onRenamed`; `App` keeps each change by id, and the notes show it at render time (AC-10).
- **The left area.** The collections area sits at the top of the left column, and the tags area below it, with a border between them (AC-08). Each area loads and fails on its own, and each keeps its own open form or confirmation, so opening a form in one leaves the other as it is (AC-08, spec question 2).
- **The review fields in the note form.** After the Tags group, the new-note and the edit form show "Review interval", a select with "None", "Daily", "Weekly", "Monthly", and "Every N days". A new note has "None", and the edit form shows the note's interval, number of days, and next review date. "Number of days" shows only while "Every N days" is chosen, and "Next review date (optional)", a date field, only while the interval is not "None". A hidden field keeps its value, so choosing its interval again shows it again, and it is neither checked nor sent (AC-12).
- **The review fields' messages.** "Create" and "Save" check them with the other fields: "Enter the number of days." when "Number of days" is empty, "Enter a whole number from 1 to 365." for anything but digits that name 1 to 365, and "Enter a valid date." when the browser reports bad input in the date field, such as a date typed in part. The server's codes show the same way, and `review_interval` `invalid` shows "Choose a review interval." (AC-12).
- **What a save sends of the schedule.** Only what the user changed (AC-12, spec question 17). The new-note form sends `review_interval` only when it is not None, `review_interval_days` (a number) only with "Every N days", and `next_review_date` only when the field holds a date. The edit form sends `review_interval` when it differs from the note's; `review_interval_days` when "Every N days" is chosen and the note had another interval or another number; and `next_review_date` when the interval is not None and the field differs from the note's date, with null for an emptied field. A save that does not touch the schedule sends no review field.
- **The schedule in the list and the detail.** Each list entry shows "Next review: Nov 16, 2026", or "No review scheduled", in an element that is not a list item (`data-testid="note-review"`). The detail shows the rows "Review interval" ("None", "Daily", "Weekly", "Monthly", "Every 10 days", or "Every 1 day" for one day) and "Next review" (the date, or "Not set") right after "Tags" (AC-12), then "Last reviewed" (the date, or "Never" for a note that was never reviewed) (AC-13).
- **Mark as reviewed.** The detail's actions start with "Mark as reviewed", before "Edit", for every note, archived ones and ones with no schedule included. It hides with the other actions while the delete confirmation is open. It sends `POST /api/notes/:id/review` with no body, and it is busy while the request waits, as in "Busy button". A 200 shows the answer's note and "Marked as reviewed." with `role="status"`. No answer, or an error answer other than 401 and 404, shows "Could not mark the note as reviewed. Try again." with `role="alert"`, and the detail stays as it was. Both show above the actions, where an archive's failure shows, and a new review removes the last one's message. A 404 and a 401 are handled as for an archive: the list shows again without the note, with "This note no longer exists.", or the sign-in screen shows (AC-13). A 200 also replaces the note's list entry, so "Back to notes" shows its new "Next review: …", as in "A note changed in its detail"; a failed review changes neither the detail nor the list (AC-14).
- **Dates.** The UI writes a review date like "Nov 16, 2026" (AC-12).
- **The filter bar.** Above the notes list, in `frontend/src/NoteFilters.tsx`: the field "Search" (an `<input type="search">`, role `searchbox`), then the drop-down lists "Collection", "Tag", "Status", and "Review", each labelled with that word and starting at "All" (AC-17, spec questions 1 and 15). "Collection" and "Tag" offer the left area's records after "All", in its order; "Status" offers "Active" and "Archived"; "Review" offers "Due today", "Overdue", "Next 7 days", and "No review scheduled", in that order (AC-15, AC-16, AC-17). The bar shows with the list in each of the list's states, and not with a note's detail or a form. `Notes` keeps the text, the search, and the choices, so they are the same after "Back to notes" or "Cancel". The address does not change, so a reload resets everything to empty and "All" (AC-15, AC-17).
- **The review state label.** "Due today" (amber) or "Overdue" (red) (`data-testid="note-review-state"`, `frontend/src/ReviewStateLabel.tsx`, one place for the words and the look of each state) shows after "Next review: <date>" in a list entry and after the date in the detail's "Next review" row (AC-16). It comes from the `review_state` the server sent, and the app never computes it. A note that is neither due today nor overdue has no label (AC-15).
- **A filtered list.** The empty states are `NO_MATCH_TEXT` and `EMPTY_TEXT` in `frontend/src/Notes.tsx`. With the search empty and only "Review" set, the list shows that choice's own message, with no button: "No notes are due for review today." ("Due today"), "No notes are overdue for review." ("Overdue"), "No notes are due for review in the next 7 days." ("Next 7 days"), "Every note has a review schedule." ("No review scheduled"); "No notes yet" stays that of "All" (AC-15, AC-16, AC-17). With anything else narrowing the list (a search, "Collection", "Tag", "Status", or "Review" together with another one), it shows "No notes match your search and filters." with the button "Clear search and filters", which empties the field, puts every list back to "All", and loads `/api/notes` (AC-17, spec question 11). The list is loaded when the main layout shows, when a choice is made, when the search runs, and on "Try again", which asks again with the current search and choices. While an answer loads, "Loading…" shows with `role="status"` in place of the entries, and the bar keeps its values and stays usable. Only the answer to the latest request is shown. A failure shows "Could not load notes. Try again." with `role="alert"` and "Try again". Opening a note and going back does not load the list, so states hold as of the list load (AC-15, AC-17).
- **The review reminders panel.** A section with the heading "Review reminders" (a region found by that name; `frontend/src/ReviewReminders.tsx`), above the notes area in the main area, whatever the notes area shows (AC-20). Its states: "Loading…" with `role="status"` until the first batch; "No review reminders" for an empty batch, with no list; and the list. Each entry shows the note's title, its collection's name, the review state label ("Due today" or "Overdue", `ReviewStateLabel`), "Next review: <date>", and the buttons "Open" and "Dismiss". After a loss, "Review reminders are offline. Reconnecting…" with `role="alert"` shows above the last list, or alone before the first batch, and it goes when a batch arrives. The panel reads only a message of the type `review_reminders`. The heading can take the focus (`tabIndex` -1). A long list scrolls inside the panel (the list has `max-h-48` and `overflow-y-auto`), so the heading "Notes" stays on the first screen. There are no toasts and no sounds.
- **Reminder entries are keyed by note, type, and date.** A batch replaces the list, and a repeated reminder keeps its element, so the focus on its button stays (AC-20).
- **"Open" and "Dismiss" in the panel.** "Open" calls `NotesHandle.openNote(id)` of `Notes` (`ref`), which shows the note's detail with the focus on its heading, and the notes area shows the list and "This note no longer exists." as an alert when the note is gone. "Open" is disabled while the notes area shows the new-note or the edit form (`onFormOpenChange` of `Notes` sets `noteFormOpen` in `App`), and works again after "Cancel", "Create", or "Save". "Dismiss" sends the `ack` of the reminder (`perform('ack', { note_id, next_review_date })`) and takes the reminder out of the panel at once, then moves the focus to the heading "Review reminders" (`tabIndex` -1), also when it was the last one ("No review reminders" shows). It has no busy state, no confirmation, and no message for an error answer, because the panel reads only `review_reminders` messages and the next batch is the truth. When the ack could not be sent (`perform` returned false), nothing changes and the reminder stays. It is disabled while offline. Both are plain buttons of the same look as "Rename" and "Delete" (AC-20, AC-24 question 4).
- **The panel's text is plain text.** React writes the title and the collection name as text, never as HTML (AC-20).
- **Narrow screens.** A window narrower than 768 CSS px is narrow; 768 px and wider is wide (AC-25). On a narrow screen a bar under the header (and under the logout alert) holds two buttons, "Collections" and "Menu", each with `aria-expanded`. "Collections" opens the collections area and "Menu" the tags area, as push-down panels across the window's width, above the reminders panel and the notes area. One panel is open at a time, and only its button opens and closes it: choosing something inside or outside a panel, or Escape in a form (which closes the form only), leaves it open. A closed panel is hidden, never unmounted, so its list, its open form, what was typed, and its confirmation stay, and the lists load at once, with the filter bar's "Collection" and "Tag" following them. Crossing 768 px switches the layout at once, with no reload and no request, and turning narrow starts with both panels closed. The header wraps onto two lines: the display name is cut with "…" and "Log out" always shows whole. The filter bar wraps with "Search" on a line of its own, note entries stack in one column, button rows wrap, and a long title, name, or address breaks inside its line. The reminders panel stays at the top of the main area, and its list is at most 12rem (`max-h-48`) high and scrolls, so the "Notes" heading shows on a 320 × 568 screen. The layout supports windows from 320 px wide; the page does not scroll sideways there (AC-25).
- **No browser storage (AC-21).** The app keeps nothing in local storage, session storage, IndexedDB, the Cache API, a service worker, or a cookie of its own, and `frontend/src/DataPrivacy.test.tsx` scans the sources for them. A feature that needs one asks for a spec change first.

## Code

- **Sign-in configuration.** `backend/config/initializers/omniauth.rb`. Credentials come from `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` for Google, and from `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` for GitHub, which requests the `user:email` scope (AC-02). Test-only placeholders apply in the test environment only.
- **Test helper.** `backend/spec/support/omniauth.rb` turns OmniAuth test mode on for every example. An example sets `OmniAuth.config.mock_auth[:google_oauth2]` (or `[:github]` for GitHub) to simulate a provider response. Tests never reach Google or GitHub (requirements.md section 7).
- **Test mode and CSRF.** OmniAuth test mode skips its request and callback phases, including the CSRF and state checks. An example that tests those checks must set test mode off in a `before` block, because the global `before` in the helper runs after an `around` block.
- **Forgery protection in tests.** `ActionController::Base` has forgery protection off in the test environment (`backend/config/environments/test.rb`), but every API controller has it on, because it inherits from `ApplicationController` (AC-05). So a request spec that sends a non-GET request first gets a real token from `GET /api/csrf` in the same session, with the `csrf_token` helper in `backend/spec/support/request_helpers.rb`. The Google and GitHub sign-in specs turn `ActionController::Base.allow_forgery_protection` on for their own examples.
- **Session and cookies.** API mode leaves out the cookie and session middleware. `backend/config/application.rb` adds them back for sign-in, with the cookie set to expire 30 days after the last request (`expire_after: 30.days`, AC-04). Any new endpoint that reads the session needs no extra setup. The store and its cookie's name are set once, with `config.session_store :cookie_store, key: "_knowledge_base_session", expire_after: 30.days`, and the middleware is added with `config.session_options`. The WebSocket connection reads the same name from `Rails.application.config.session_options[:key]` (AC-22).
- **Forgery protection in API controllers.** `ApplicationController` includes `ActionController::RequestForgeryProtection` and runs `protect_from_forgery with: :exception`, so every API controller checks requests that change data (AC-05). `Api::CsrfController` still includes the module itself, because it calls `form_authenticity_token`.
- **Frontend tests.** `frontend/src/App.test.tsx` replaces `fetch` with `vi.stubGlobal` and answers `/api/session` and `/api/csrf` per test. Wait for asynchronous UI with `findBy` or `waitFor`. A test that renders the main layout also answers `GET /api/collections`, with an empty list (AC-06) Every test file runs on top of the network guard (AC-27).
- **Current user and sign-in check.** `current_user` in `ApplicationController` is the user of this browser's live sign-in (`current_sign_in`). Every endpoint that reaches a user's data uses `current_user`, never the session's user id alone. `require_signed_in_user`, run with `prepend_before_action`, answers 401 before the token check (AC-05, AC-06). `current_sign_in` calls `SignIn.of_session(session)` (`backend/app/models/sign_in.rb`), the one lookup by the session's `sign_in_token` and `user_id`, which the WebSocket connection uses too. `SignIn#ended?` asks the database whether the sign-in's row still exists (AC-22).
- **Errors in `ApplicationController`.** A missing or wrong anti-forgery token answers 403 `invalid_csrf_token`. A body that is not JSON answers 400 `bad_request`. `ActiveRecord::RecordNotFound` answers 404 `not_found`. `render_validation_failed(record)` answers 422 with one code per field, built from the record's errors (AC-06).
- **Name rules.** `Collection` and `Tag` include the `UniquelyNamed` concern (`backend/app/models/concerns/uniquely_named.rb`). The concern holds the tidying, the length, the uniqueness per user ignoring case, and the alphabetical scope (AC-06, AC-08).
- **Sending a change from the browser.** `frontend/src/api.ts`, `sendWithCsrfToken(method, url, body?)`, fetches a token from `GET /api/csrf` right before the request and sends it in `X-CSRF-Token`. The body, when there is one, is sent as JSON. Logout gets its token the same way, in `frontend/src/App.tsx` (AC-05, AC-06).
- **A list of named records.** `frontend/src/NameListArea.tsx` is the one component that lists, creates, renames, and deletes a user's named records: the list, its states, the forms, and the delete confirmation. Frontend tests: jsdom has no `matchMedia`, so `frontend/src/test/screen.ts` provides a stand-in (it answers `(width < Npx)`, `(max-width: Npx)`, and `(min-width: Npx)`, and `setWindowWidth(px)` sets `window.innerWidth` and fires "change", inside `act`), assigned in `src/test/setup.ts` as `window.matchMedia`, and every test is 1280 px wide unless it calls `setWindowWidth`. `frontend/src/ResponsiveLayout.test.tsx` holds the AC-25 tests. Verify sets the exact window sizes with Playwright (320 × 568, 375 × 667, and widths 767, 768, 1280) and checks "fits": `document.documentElement.scrollWidth <= clientWidth` (AC-25).
- **Test names and the test mapping (AC-29).** `backend/lib/test_mapping.rb` (with `backend/lib/test_mapping/`) reads the test files and the plans, never runs a test, and builds `specs/docs/test_mapping.md`. A test's name is plain text: one string literal with no interpolation, and it starts with its AC IDs, two of them separated by a space (`"AC-13 AC-14 ..."`). No `it.each`, no name built from a variable, no fixture line in a spec that looks like a test. A test with no ID, an unknown ID, or a name that is not plain text is listed under "Tests with no known AC", and the check fails. The keywords it knows: in RSpec `it`, `specify`, `example`, `scenario`, their focused forms (`fit`, `fspecify`, `fexample`, `fscenario`), and their skipped forms (`xit`, `xspecify`, `xexample`, `xscenario`, and `skip` or `pending` when the line opens a block); in Vitest `it` and `test`, alone or with `.only`, `.skip`, `.todo`, `.concurrent`, `.sequential`, `.fails`, or `.each`. Groups (`describe`, `context`) are not tests. A skipped test is listed with " (skipped)" and is not counted. Two commands, both defined in `backend/lib/tasks/test_mapping.rake`: `docker compose run --rm backend bin/rails test_mapping:write` writes the file, and `docker compose run --rm backend bin/rails test_mapping:check` changes nothing and exits 1 when the file is out of date, a test has no known AC, or a test named in the README's "Test coverage" table does not exist. The table has the columns `| Case (requirements.md 7) | AC | Tests |`, with each test as `` `<file from the repository root>`: "<full name>" ``, separated by `<br>`, and a `"` or `|` inside a name written `\"` or `\|`. Polish of every feature from AC-29 on runs `write` and then `check` as its last step, and `bin/test` does not run the check, so a new test never fails the suite for a stale file. The specs of the generator (`backend/spec/lib/test_mapping_spec.rb`, `backend/spec/tasks/test_mapping_task_spec.rb`) build their repositories in a temporary folder with the shared context in `backend/spec/support/test_mapping_fixtures.rb`, which stubs `TestMapping.root`; they never read the real tests, and the Rake tasks are loaded once per RSpec process by `rake_helpers.rb`.
