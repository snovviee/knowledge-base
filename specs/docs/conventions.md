# Conventions

## UI

- **Loading.** While the app checks the session, the page shows a status line "Loading…" with `role="status"`. The app does not flash the sign-in screen first (AC-01, AC-04).
- **Sign-in error.** A failed or cancelled sign-in comes back as `?sign_in_error=google` or `?sign_in_error=github`. The sign-in screen names that provider: "Sign-in with Google did not complete. Try again." or "Sign-in with GitHub did not complete. Try again." It is shown with `role="alert"`, and the parameter is removed from the address (AC-01, AC-02).
- **Busy button.** After either sign-in button is chosen, both sign-in buttons are disabled and have `aria-busy="true"`, so a second click starts no second sign-in (AC-01, AC-02).
- **Empty states.** The main layout shows "No collections yet" in the collections area (AC-01, AC-06), "No tags yet" in the tags area (AC-08), and "No notes yet" in the notes area (AC-01). Later features keep the same wording rule.
- **Loading inside an area.** An area that loads a list shows "Loading…" with `role="status"` in its own place, while the rest of the layout shows (AC-06).
- **Load error with Try again.** A list that cannot load shows "Could not load collections. Try again." (or the area's own message) with `role="alert"` and a "Try again" button. The button shows "Loading…" and loads the list again (AC-06, AC-04).
- **Forms in place.** A create or rename form opens in its place in the list, with the focus in its name field. "Cancel", Escape, or opening another form closes it with no request. One form or confirmation is open at a time. The create, save, and delete buttons are busy while their request waits, the same way as the sign-in buttons (AC-06).
- **Validation messages.** A refused name shows its message under the field, with `role="alert"`. The field gets `aria-invalid="true"` and `aria-describedby`. The messages are "Enter a name." (`blank`), "Use at most 100 characters." (`too_long`), and "A collection with this name already exists." (`taken`). The first two are in `frontend/src/NameListArea.tsx`, and the third is in `frontend/src/Collections.tsx` (AC-06).
- **Change failures.** A create, rename, or delete with no answer, or with an error answer, shows "Could not create the collection. Try again.", "Could not rename the collection. Try again.", or "Could not delete the collection. Try again." as an alert. The form or the confirmation stays open with the typed name (AC-06).
- **A refused delete.** A collection that still has notes is not deleted. Its delete confirmation stays open and shows "This collection still has notes. Move or delete them first." as an alert, in place of the general failure above. "Delete" can be chosen again once the notes are gone. Tags have no refusal, so their confirmation shows only the general failure (AC-07).
- **Delete confirmation.** The row asks "Delete “<name>”? This cannot be undone." with "Delete" and "Cancel". The focus is on "Cancel", and only "Delete" sends the request (AC-06).
- **A record that is gone.** A rename or delete answered 404 takes the row off the list. A rename also shows "This collection no longer exists." as an alert (AC-06).
- **Sign-in ended.** A list or change request answered 401 shows the sign-in screen with no message (AC-05, AC-06).
- **Logout.** The header shows the display name and a "Log out" button. The button is busy while its request waits. A failed logout shows "Could not log out. Try again." with `role="alert"` under the header, and the main layout stays (AC-05).
- **Server error on page load.** When the session check cannot reach the server, or gets an answer other than success or 401, the page shows "Could not reach the server. Try again." with `role="alert"` and a "Try again" button. The button checks the session again. The sign-in screen does not show (AC-04).

- **The notes area.** It shows one view at a time, in place: the list, a note's detail, the new-note form, or the edit form. "Back to notes" returns to the list, and the address does not change (AC-09). "No notes yet" is its empty state, and "New note" opens the form.
- **Browser checks on submit.** "Create" and "Save" check the fields first. Each field that breaks a rule shows its message under it, is marked `aria-invalid`, and the first such field gets the focus. Nothing is sent. The messages are "Enter a title.", "Use at most 200 characters.", "Enter a body.", "Use at most 100,000 characters.", "Enter a URL that starts with http:// or https://.", "Use at most 2,000 characters.", and "Choose a collection." The server's 422 answer shows its codes the same way, and "This collection no longer exists. Choose another." for `collection_id` `not_found` (AC-09).
- **Note failures.** A note create, save, archive, restore, or delete with no answer, or with an error answer, shows "Could not create the note. Try again.", "Could not save the note. Try again.", "Could not archive the note. Try again.", "Could not restore the note. Try again.", or "Could not delete the note. Try again." The form, the detail, or the confirmation stays open (AC-09).
- **Escape.** Escape does not close the note form, so a long body is not thrown away by a stray key. Escape does cancel a delete confirmation (AC-09).
- **Focus.** An opened detail puts the focus on the note's title. A delete confirmation puts it on "Cancel" (AC-09).
- **A renamed collection.** A collection renamed in the collections area shows its new name on its notes, in the list and in an open detail, with no notes request. `NameListArea` takes an `onRenamed` callback for areas that show a collection's name; `App` keeps each rename by id, and `Notes` shows it at render time (AC-09).
- **The Tags group in the note form.** The new-note and the edit form show a "Tags" group, one checkbox per tag. The group loads the tags on its own, while the rest of the form works (AC-10). Its states are "Loading…" with `role="status"`, "Could not load tags. Try again." with "Try again" when the tags cannot load, and "No tags yet" when the user has none.
- **A chosen tag that no longer exists.** When a create or a save answers 422 with `tag_ids` `not_found`, the group shows "A chosen tag no longer exists. Check the tags again." with `role="alert"`, loads the tags again, keeps the checks of the tags that still exist, and moves the focus to the group. The form keeps what was typed (AC-10).
- **Tag names in the list and the detail.** A note's tags show after its collection's name in the list, as plain text in an element that is not a list item, and as "Tags" with the names, or "No tags", in the detail (AC-10).
- **A tag's delete confirmation.** The tags area's confirmation adds the line "Notes with this tag are kept." under "Delete “<name>”? This cannot be undone.". Collections have no such line (AC-10).
- **A renamed or deleted tag.** A tag renamed in the tags area shows its new name on its notes, and a deleted tag leaves them, in the list and in an open detail, with no notes request. `NameListArea` takes an `onDeleted` callback as well as `onRenamed`; `App` keeps each change by id, and the notes show it at render time (AC-10).
- **The left area.** The collections area sits at the top of the left column, and the tags area below it, with a border between them (AC-08). Each area loads and fails on its own, and each keeps its own open form or confirmation, so opening a form in one leaves the other as it is (AC-08, spec question 2).

## Code

- **Sign-in configuration.** `backend/config/initializers/omniauth.rb`. Credentials come from `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` for Google, and from `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` for GitHub, which requests the `user:email` scope (AC-02). Test-only placeholders apply in the test environment only.
- **Test helper.** `backend/spec/support/omniauth.rb` turns OmniAuth test mode on for every example. An example sets `OmniAuth.config.mock_auth[:google_oauth2]` (or `[:github]` for GitHub) to simulate a provider response. Tests never reach Google or GitHub (requirements.md section 7).
- **Test mode and CSRF.** OmniAuth test mode skips its request and callback phases, including the CSRF and state checks. An example that tests those checks must set test mode off in a `before` block, because the global `before` in the helper runs after an `around` block.
- **Forgery protection in tests.** `ActionController::Base` has forgery protection off in the test environment (`backend/config/environments/test.rb`), but every API controller has it on, because it inherits from `ApplicationController` (AC-05). So a request spec that sends a non-GET request first gets a real token from `GET /api/csrf` in the same session, with the `csrf_token` helper in `backend/spec/support/request_helpers.rb`. The Google and GitHub sign-in specs turn `ActionController::Base.allow_forgery_protection` on for their own examples.
- **Session and cookies.** API mode leaves out the cookie and session middleware. `backend/config/application.rb` adds them back for sign-in, with the cookie set to expire 30 days after the last request (`expire_after: 30.days`, AC-04). Any new endpoint that reads the session needs no extra setup.
- **Forgery protection in API controllers.** `ApplicationController` includes `ActionController::RequestForgeryProtection` and runs `protect_from_forgery with: :exception`, so every API controller checks requests that change data (AC-05). `Api::CsrfController` still includes the module itself, because it calls `form_authenticity_token`.
- **Frontend tests.** `frontend/src/App.test.tsx` replaces `fetch` with `vi.stubGlobal` and answers `/api/session` and `/api/csrf` per test. Wait for asynchronous UI with `findBy` or `waitFor`. A test that renders the main layout also answers `GET /api/collections`, with an empty list (AC-06).
- **Current user and sign-in check.** `current_user` in `ApplicationController` is the user of this browser's live sign-in (`current_sign_in`). Every endpoint that reaches a user's data uses `current_user`, never the session's user id alone. `require_signed_in_user`, run with `prepend_before_action`, answers 401 before the token check (AC-05, AC-06).
- **Errors in `ApplicationController`.** A missing or wrong anti-forgery token answers 403 `invalid_csrf_token`. A body that is not JSON answers 400 `bad_request`. `ActiveRecord::RecordNotFound` answers 404 `not_found`. `render_validation_failed(record)` answers 422 with one code per field, built from the record's errors (AC-06).
- **Name rules.** `Collection` and `Tag` include the `UniquelyNamed` concern (`backend/app/models/concerns/uniquely_named.rb`). The concern holds the tidying, the length, the uniqueness per user ignoring case, and the alphabetical scope (AC-06, AC-08).
- **Sending a change from the browser.** `frontend/src/api.ts`, `sendWithCsrfToken(method, url, body?)`, fetches a token from `GET /api/csrf` right before the request and sends it in `X-CSRF-Token`. The body, when there is one, is sent as JSON. Logout gets its token the same way, in `frontend/src/App.tsx` (AC-05, AC-06).
- **A list of named records.** `frontend/src/NameListArea.tsx` is the one component that lists, creates, renames, and deletes a user's named records: the list, its states, the forms, and the delete confirmation. It takes the path, the JSON keys, the words, and the test id as props (AC-06, AC-08). `frontend/src/Collections.tsx` and `frontend/src/Tags.tsx` each pass only their own words and settings.
- **The collections and tags areas.** `frontend/src/Collections.tsx` and `frontend/src/Tags.tsx` hold each area's words. The tags area shows "Tags" as its heading, "New tag" to open the create form, and "Tag name" as the field label, with "No tags yet" when the list is empty. Its load failure is "Could not load tags. Try again.", its refused name is "A tag with this name already exists.", and its change failures are "Could not create the tag. Try again.", "Could not rename the tag. Try again.", and "Could not delete the tag. Try again." Its tests are in `frontend/src/Tags.test.tsx` (AC-08).
- **Notes frontend.** `frontend/src/Notes.tsx` is the notes area and holds the list and the one-view-at-a-time state. `frontend/src/NoteDetail.tsx` is a note's detail, with its actions and its delete confirmation. `frontend/src/NoteForm.tsx` is the new-note and edit form; its browser checks are `checkNote`. Each renders a loaded note from the server, and the 401 and 404 answers are passed up to `App` and to `Notes` (AC-09).
- **Notes backend.** `backend/app/models/note.rb` holds the note's rules, and `backend/app/controllers/api/notes_controller.rb` the five endpoints. Its lookups go through `current_user.notes`, so another user's note is `not_found` (AC-09).
- **Notes tags frontend.** `frontend/src/NoteTags.tsx` is the Tags group, and it holds the loading, the failure, the refusal, and the checked set. `frontend/src/tagChanges.ts` applies a renamed or deleted tag to a note's tags at render time, for the list and the detail (AC-10).
- **Notes tags backend.** `backend/app/models/note_tag.rb` is the link. `Note` and `Tag` have their `has_many` associations, and `Note#add_tag` adds a tag once. The controller's `set_tags` writes a note's tags in the same transaction as the note, and `tags_of_the_user` refuses a tag that is not the user's (AC-10).
- **Main-layout test stubs.** Every test that renders the main layout answers `GET /api/notes` as well as `GET /api/collections` and `GET /api/tags`. `frontend/src/Notes.test.tsx` renders `<App />` with a fetch stub that answers by method and path (AC-09).
- **Named-record model concern.** `backend/app/models/concerns/uniquely_named.rb` holds the name rules for a model whose name is unique per user: the tidying, the length, the uniqueness ignoring case, and the alphabetical scope. `Collection` and `Tag` include it (AC-06, AC-08).
- **Frontend tests for the areas.** `frontend/src/Collections.test.tsx` renders `<App />` with a fetch stub that answers by method and path (AC-06). `frontend/src/App.logout.test.tsx` covers logout (AC-05).
- **Request-spec helpers.** `backend/spec/support/request_helpers.rb` has `sign_in_with_google(browser = integration_session, uid:, name:)` and `csrf_token(browser = integration_session)`, used by `backend/spec/requests/logout_spec.rb` and `collections_spec.rb` (AC-05, AC-06).
- **Creating a record from a sign-in.** `find_or_create_user` in `backend/app/controllers/auth/sessions_controller.rb` looks up the account, creates it on the first sign-in, and on a duplicate uses the record the other request created. It rescues the duplicate and any other invalid record, then looks the account up again. A duplicate finds the other request's record. Any other invalid record finds nothing and returns no user, so the sign-in takes the failure redirect (AC-03).
- **Race tests.** A lost race is tested by stubbing `User.find_by` to miss once for the account, so the create reaches the duplicate (`backend/spec/requests/auth/user_auto_create_spec.rb`) (AC-03).
